Requirements

Specification verification and source traceability for PHP 8.1+.

Keep the original text, an EARS specification and its executable tests together. Find unaccounted source units, changed quotations, independent specifications and unsupported behavior with recorded reasons. Upstream requirements are optional.

composer require --dev k-kinzal/requirements
vendor/bin/requirements lint
vendor/bin/requirements check
vendor/bin/requirements coverage
vendor/bin/requirements spec
vendor/bin/requirements list --without-source

In this monorepo, run composer install in packages/requirements, then use php ../requirements/bin/requirements from the package being checked. The tool's PHPUnit/Behat adapters execute that package's configured binaries. They are runner extensions of requirements; no PHPUnit/Behat bootstrap extension is required.

See the requirements and design, the document format and extension contracts. Run the small complete example with bin/requirements coverage --config examples/requirements.yaml.

Commands

CommandResult
checkVerify full quoted units against the selected source scope
coverageReport global and per-source accounted/supported/unsupported/uncovered units and enforce gates
specExecute linked tests and report each specification as passed, failed, unverified or unsupported
listList specifications/requirements, provenance, rationale, labels and references
lintValidate documents, IDs, EARS form, extension registration and the cross-file graph without fetching sources or running tests
formatNormalize YAML indentation and scalar formatting; --check detects drift without writing

Every command accepts --config FILE (default requirements.yaml) and --json. list and spec accept --id, --label, --category, --source, --status, --kind, --origin and --without-source. Filters combine with AND and use exact values. --source selects the definition's source ID; inherited source links are available in the requirement graph. An empty spec selection fails.

check and coverage accept --live to fetch source URIs instead of snapshots. Default mode uses verified snapshots where configured, otherwise the URI. Source adapters cache content only for the current command. format rewrites YAML and removes comments; keep explanatory material in reason, design or metadata.

Exit codes: 0 success, 1 failed check, gate, verification or format check, 2 invalid configuration, options or an unrecoverable error. Source failures appear in reports and fail checks; they never count as full coverage.

What coverage means

The denominator is the union of source units enumerated by each URI + selector, not the whole website, manual or repository. A unit is an explicitly selected DOM element, JSON value or nonblank text line. Identical locations count once across scopes. Equal text at different locations remains distinct. Choose granular scopes and review them as carefully as specifications.

A specification with valid evidence accounts for its units. Evidence inherited through requirements also counts. A requirement without a specification does not. Reasoned unsupported specifications count as accounted but are reported separately from supported behavior. Unsupported items are not executed or called implemented. Independent specifications add no source units. Uncovered units and reverse links from units to specification IDs appear in the JSON report's units map.

A quotation must match an entire selected unit after whitespace normalization. The checker detects missing or changed text, ambiguous selectors and out-of-scope citations. It does not prove that the EARS statement faithfully interprets the quote, that a paragraph contains only one obligation, or that a test adequately asserts the behavior. Those relationships remain review decisions. Coverage and test results are deliberately separate metrics.

CI and differential gates

coverage:
  minimum: 80
  sources:
    grammar-manual: 90
  diff_minimum: 100
requirements lint
requirements format --check
requirements check
requirements coverage --baseline /tmp/base-coverage.json
requirements spec

Generate a baseline using requirements coverage --write-baseline requirements-baseline.json. Commit it for comparison by later changes. During pull-request CI extract the baseline from the trusted base revision, not from the pull request's updated file:

git show "origin/$GITHUB_BASE_REF:packages/example/requirements-baseline.json" > /tmp/base-coverage.json
requirements coverage --baseline /tmp/base-coverage.json --min-diff-coverage 100

Fetch the base ref first. On the initial adoption PR no base report exists, so use the total gate and review the initial scope. --min-coverage and --min-diff-coverage override configured thresholds. A configured positive diff threshold requires a baseline. Unchanged units have no differential denominator (percentage: null) and pass. New/changed unit text or claiming records form the differential denominator. This includes changed statements, status, reason, requirements and test references. Removed units are listed and fail unless the scope reduction was reviewed and --allow-removed is explicitly supplied.

spec deduplicates runner/target pairs and runs each selection in a subprocess with a timeout and fresh JUnit directory. Passing requires exit 0, at least one reported test and no skipped, pending, undefined, failed or errored tests. All tests linked to a specification must pass. A supported specification with no tests is unverified and fails. Commands are argument arrays, not shell strings.
