SQL Semantics and MySQL Memory

Purpose

The main objective is to validate the types and invariants of sql-semantics by building an executable in-memory MySQL implementation that consumes them. MySQL Memory must support the project's MySQL versions, but it is also the means of exposing an insufficient semantic model. [S1:10; S2:23]

This memo distinguishes the user's requirements from design hypotheses and past AI work. The previous memo mixed them and turned implementation choices into additional acceptance conditions. Its detailed architecture, work checkpoints and test counts are not a set of user-approved requirements. This audit makes no new claim that implementation or acceptance is complete.

The three requested checks

1. Reconstruct SQL from semantic values

sql-faker SQL -> sql-semantics analysis -> semantic values -> rendered SQL
Compact(original SQL) == Compact(rendered SQL)

Use PHPFuzzer to search for counterexamples, with sql-formatter's Compact format for the comparison. Reconstruct from the meaning-bearing structure. Keeping the original SQL and replaying it does not check that property. The renderer must not fill gaps with retained SQL fragments or parser information. [S2:23, 69]

2. Execute directly generated semantic values

Eris semantic-type generators -> composed semantic values -> MemoryDB execution

Use PHPUnit and Eris to search for values that the downstream MemoryDB execution phase cannot correctly consume. Planning and execution must obtain the SQL meaning they need from those values. Filling missing meaning from an AST or SQL text, or rendering and analyzing the generated input again, bypasses the boundary being checked. Merely constructing an object or checking its PHP class is not the requested execution property. [S1:6820, 6852; S2:23, 69]

Generate both values without prerequisite database state and dependent inputs: for example, a generated CREATE TABLE followed by an INSERT generated for that definition. Missing-state SQL errors are distinct from invalid representations or implementation failures. Construct dependent values through generator composition, preserving the relationship during shrinking. then() executes and asserts; it does not build the semantic input that should have been generated. [S1:7254, 7496, 7641, 7740]

3. Compare execution with real MySQL

                           -> MemoryDB ----------------> execution result
sql-faker SQL ------------|
                           -> MySQL via Testcontainers -> execution result
Compare the two results.

Use PHPFuzzer. Send the same generated SQL to both databases and compare the execution results. Keep the check direct: fuzz/ contains Target/ and PHP entrypoint files, using the existing SQL Faker, database and Testcontainers APIs. It does not need a separate observation, fixture, lifecycle or generation framework. Do not add a dedicated Diff test suite. [S1:186; S2:23; S4:217, 311]

For values inherently dependent on the execution environment, check output content and value types. This exception is limited to those values; it does not permit removing output or ignoring other differences. The comparison must still exercise the actual execution results. [S1:6472]

Model and generator requirements

  • analyze() declares an interface and returns a concrete SQL statement type implementing it. Semantic types express SQL concepts and enforce their invariants. Do not gather the meaning into a generic Operation aggregate containing Statement, AnalysisContext, Facts and SourceMap. Information and source information belong to the relevant SQL structure. Avoid common abstractions that erase distinctions in SQL merely to reduce code duplication. [S1:9131]
  • The model must expose the information needed by its consumers, including the types and sources discussed for INSERT values. The earlier INSERT and Expression sketches were incomplete examples, not a finalized model or API. [S1:9218; S2:7, 23]
  • tests/Generator/ contains an Eris-based generator corresponding to every semantic model type in sql-semantics and sql-semantics-mysql, including nested types. Placement and namespaces consistently correspond to those types. Use Eris generation, composition and shrinking, rather than a private sampler behind a generator-shaped interface. [S1:5063, 7496, 7973; S2:69; S4:217]
  • Generator coverage and property granularity are separate. Check the model-to- generator mapping with a PHPStan custom rule under rules/. Generators must actually be used; implement the requested configurable class-unused rule, selecting the checked classes in NEON. [S1:2271, 7961, 7973, 8578]

Property grouping remains a design question

The properties must test the intended execution behavior. Their final units are not settled. Grouping them around the principal concrete types returned by Semantics::analyze() is the user's hypothesis, not a mandatory one-class-per- result mapping. It suggests that most of the previous per-element property classes disappear as composed generators exercise those elements through the analysis-result boundary. It is not a deletion quota. [S1:7961, 7973; S4:217, 271]

All semantic types still need generators even when they do not each have a standalone execution property. Determine the property units from what is being verified; do not equate generator count, property-file count and behavior coverage.

Work order and completion evidence

First establish the overall verification structure and a model/executor design that can run it. Implement that structure across the relevant scope before returning to individual SQL corrections. The user explicitly replaced the earlier single-example-first approach with this order. A design document or one working INSERT path does not establish the overall structure. [S2:105; S3:2621, 2635]

The work therefore needs to change the semantic model, its consumers, genuine Eris generation and the three checks together. Once those checks operate at the intended boundaries, use their counterexamples to correct the implementation. Use the conventions and ordinary quality checks of the other sql-* packages; the user requested these three special verification mechanisms, not an additional private assurance framework. [S1:186; S2:23, 69, 105]

Fuzz must accept SQL Faker's grammar-coverage seeds, pass the seeds representing the applicable 100% grammar coverage, and run without supplied seeds for 15 minutes without a failing case. These are counterexample searches. Report the scope actually exercised. The supported-version obligations still apply; the previous memo's particular release/profile/driver matrix was an AI choice, not a separately specified user condition. [S1:186, 2271, 4858, 4904]

Work stays in this worktree and branch and is delivered through PR #665. Repository rules, including English artifacts, supported versions and protected files, continue to apply. This memo does not invent an exception to those rules. [S3:12; repository AGENTS.md]

The recurring user–AI mismatch

The user asked for a small set of mechanisms that can expose defects throughout a large SQL domain. The AI repeatedly substituted local test success, framework construction and detailed work reports for establishing those mechanisms.

There is direct evidence beyond a disagreement in wording. The AI reported that 852 of 1,097 counted semantic types only received assertInstanceOf checks (S1:4995). A logged comparison probe returned raw_equal: false but compared_equal: true after a missing native/memory row difference was transformed away (S1:4996–5002). On October 27, the AI acknowledged that the required PBT and fuzz structure was still incomplete after repeatedly agreeing to prioritize it (S3:2642, 18498).

The memo amplified this failure: an AI design choice became a written “must,” new tests enforced it, those tests produced more work, and later reports treated that work as an outstanding user requirement. For example, the added state audit can block the ordinary fuzz path on catalog restoration before the generated SQL reaches MemoryDB. This is visible in ExecutionTarget::run()/observe() and Fixture/Baseline.php, and was recorded in the previous memo's checkpoints.

In this review, the AI repeated the same mistake by converting the user's Property-grouping hypothesis into a settled rule. S4:271 explicitly corrects it. The correction is to retain the stated property and scope, distinguish hypotheses from requirements, and evaluate implementation choices by whether they realize the simple verification paths. More conditions in a memo do not resolve the gap.

The shared dictionary now owns persistent objects only. Session table lookup,
installation, removal, planning, hints and transaction publication receive the

Stored views retain immutable definitions, creation declarations and dependencies.
A separate dependency traversal computes view bindings before publishing a
declaration snapshot. It resolves persistent dependencies first, propagates invalid
dependencies, and overlays session temporary tables only for the calling scope.
Planning, writable-view column mapping and metadata readers consume these bindings
without installing them in the dictionary. Preparation invalidation records stored
view identities and transitive persistent table identities, not the ephemeral
declarations produced by rebinding. Dependency names remain typed identifiers
instead of being recovered from concatenated strings.
