These rules override every other note in this memo and every existing piece of code. The user had to correct the agent repeatedly on these points; the corrections are recorded here so that they are not lost and not reinterpreted.

  1. What PBT is. Eris generators generate the types of SQL Semantics analysis results. Those generated values run MemoryDB's phases after analysis. The property is that no error occurs. The only allowed exception is an error that depends on database state, such as a table definition that does not exist. That is the whole property. Write it plainly; the user does not want a clever formulation.
  2. What a generator is. Every class under tests/Generator is a final XxxGenerator that implements Eris\Generator. Its constructor composes one delegate generator from the generators of the type's operands, following the type's structure and invariants, and nothing else. __invoke and shrink forward to the delegate. There is no other method. The canonical shape is:
   final class OrderItemGenerator implements ErisGenerator
   {
       private ErisGenerator $delegate;

       public function __construct()
       {
           $this->delegate = Generators::map(
               static fn (array $data): OrderItem => new OrderItem(sku: $data['sku'], quantity: $data['quantity'], unitPriceYen: $data['unitPriceYen']),
               Generators::associative([
                   'sku' => Generators::elements('SKU-A', 'SKU-B', 'SKU-C'),
                   'quantity' => Generators::choose(1, 100),
                   'unitPriceYen' => Generators::choose(0, 10000),
               ])
           );
       }

       public function __invoke($size, RandomRange $rand) { return ($this->delegate)($size, $rand); }

       public function shrink(GeneratedValue $element) { return $this->delegate->shrink($element); }
   }
  1. What must not exist. forms(), additionalForms(), executionForms(), operands(), fromOperands(), selecting(), withPrerequisites(), refused*() and every other method beyond the three above are not part of a generator. Enumerated fixed statement forms such as 'AlterTable/253' are not derived from the type's structure and break the generator. Narrowing the candidates of an enum and substituting component generators have no place either, not even through constructor arguments: they distort the property that is to be established. The agent's proposal to allow narrowing and substitution through constructor arguments was wrong.
  2. Enforcement. A PHPStan rule checks the shape: under Tests\Generator every class is a final XxxGenerator, implements Eris\Generator, declares __invoke and shrink, and declares no other method. The rule is added first, every generator is made to pass it, and only then is the rest of the goal pursued.
  3. No invented roles. The agent's remark that fixed statement forms belong to sql-faker was unrelated and wrong. sql-faker is the grammar-based SQL generator of the fuzz comparison; it has no role in the Eris generators of semantic types.
  4. Plain work. The user is not asking for the property to be done well; the user is asking for it to be done plainly. Attempts to do it cleverly produced the errors above and cost the user time.

The type property SQL Semantics must have (user's review of 2026-10-31, mandatory)

The user reviewed the PBT results and corrected the direction of the work. These points are binding.

  1. The analysis-result types are type-safe and protected by invariants: a value that can be instantiated is executable SQL, except for conditions that depend on database state. MemoryDB exists to measure whether SQL Semantics' structured types have this property. The PBT exposed that they do not: the generators instantiated values the server rejects.
  2. The statementInformation record (diagnostics and warnings) mixes three different things and is therefore wrong as a structure.
    • Problems of the structure itself (DuplicateColumn, Misuse, MisplacedPrivilege, ...) are violations of the type's invariants. The constructor must refuse them; the analysis must fail with an error instead of returning a value.
    • ParseFailure and ParseStop are analysis errors. They are never part of a value.
    • Conditions that depend on database state (MissingTable, MissingColumn, UndeclaredVariable, ...) are MemoryDB's responsibility. State management belongs to MemoryDB; the type carries only the name. If the structure could be built, it must run.
    • Deprecation and the other release-dependent notices are properties of the type. Whether a warning is raised is decided by the consumer (MemoryDB) from the type and the release, not recorded in the value.
  3. MemoryDB must not compensate for the type. Mapping recorded diagnostics to server errors, or filtering generated values after construction (Analysis::accepted, Operands), hides the broken property instead of fixing it. Both are removed as the types are corrected.
  4. The work proceeds in this PR without further confirmation: classify every diagnostic and warning class (table below), then change the types, the analysis, MemoryDB and the generators category by category, verifying each step with the fuzz replay and the PBT.

Stored program bodies are read, not executed (verified on 8.4.7 and 5.7.44)

CREATE PROCEDURE reads its body with the grammar and performs only the checks the parser performs while reading: syntax (1064, including built-in function arity), unknown collation (1273), cast precision and width (1426, 1439), unknown system variable (1193), unknown EXPLAIN format (1791), unknown storage engine (1286). Everything that needs name resolution or structural consistency is deferred to CALL: unknown tables, columns and functions, GROUP BY, value counts, partitions, sql_mode values, SELECT ... INTO arity, duplicate columns, several primary keys and empty definitions of CREATE TABLE, duplicate ALTER TABLE columns.

Consequently a body member has a different meaning from the standalone statement: it is bound to definitions and given its exact semantics only when the routine is called (the user's formulation). The model keeps the two apart:

  • The standalone statement type carries the execution invariants (class I above).
  • A body member is a stored form (Deferred*, the existing convention) whose invariants are the parser's reading-time checks only. Statement kinds that lack a stored form get one. MemoryDB constructs the executable type from the stored form when the routine runs and reports that construction's refusal as the server error.
  • The reading-time checks the server performs in bodies and standalone alike are the ParseFailure class: they are analysis errors, never values.

Where the server finds a refused condition: while parsing or after (verified on 5.6.51, 5.7.44 and 8.4.7)

A RejectedInput carries aborts. It records which of two moments the server finds the condition in, because MemoryDB orders the diagnostics area from it:

  • aborts = true: found while parsing, and parsing stops. Nothing written after it is read. MemoryDB (Reader::rejection) collects the notices up to end and reports the error.
  • aborts = false: either found while parsing without stopping (the server records it and keeps reading: an expression COLLATE name on 8.0+), or found after the whole statement is read (a condition checked at contextualization or execution). MemoryDB (ContinuingRefusal) collects every parse-time notice and parse-time error of the statement first, reports the first parse-time error if there is one, and otherwise the refusal. When no database is selected and an unqualified table name is written before end (Entry\ImplicitTables; common table expression names, SHOW targets with their own FROM db, and empty names excepted), the server opens that table first and MemoryDB reports No database selected.

Goal and authority

Build MySQL Memory so that it correctly executes SQL Semantics' meaning-bearing, structured values after analysis, and verify its behavior against real MySQL. The required verification consists of two mechanisms:

  1. PHP-Fuzzer generates SQL through SQL Faker and compares execution on MemoryDB with execution on real MySQL started through Testcontainers.
  2. PHPUnit/Eris generates SQL Semantics values and executes MemoryDB's phases after SQL Semantics analysis. PHPStan rules guarantee corresponding generators exist for all semantic model types.

The user's latest clarification governs this memo. It supersedes the previous "three checks" description and the previous blanket permission to accept SQL errors in PBT. SQL -> semantic model -> SQL reconstruction is not required. Its earlier test results do not satisfy either mechanism above and must not be reported as progress toward their acceptance conditions.

This memo records requirements, observed implementation state, and remaining work separately. Existing code, previous agent plans, test counts and old goal labels do not create requirements. Historical notes remain in Git history rather than being repeated here as competing instructions.

Required verification

PHP-Fuzzer: compare execution with real MySQL

                                             via Testcontainers

                                  +-- compare ---+

The normal fuzz path uses MemoryDB and one real database. The rule about real-database differences does not require three databases, two native servers per trial, or a second native execution for every generated input.

Only differences that also occur between real database executions under comparable versions, settings and input histories may be accepted as differences. A MemoryDB limitation, a plausible "environmental" explanation, or two values having the same PHP type is not sufficient. Any exception needs evidence for the particular real-database variability and must remain limited to that variability. Deterministic result content must still match. Do not delete rows, columns, diagnostics or other mismatches to obtain a passing comparison.

SQL errors in this differential check are observable execution results: compare the actual errors and any partial results. Matching native and MemoryDB SQL errors are distinct from PBT's success property below. MemoryDB implementation failures must fail the fuzz run even if a transport presents them as SQL errors.

The two required fuzz acceptance results are:

  • A successful 15-minute run without supplied corpus seeds, starting with an empty corpus and still generating SQL through SQL Faker.
  • Successful execution comparison for all SQL Faker seeds establishing 100% grammar coverage of the applicable grammar. Verify the corpus against SQL Faker's coverage contract; neither a file count nor a partial replay proves success. Do not omit failing productions or narrow the grammar to pass.

Record the source revision, database release, grammar/profile, commands, completed inputs, elapsed time and failures. A recorded mutation RNG seed is useful for reproduction and is not a supplied corpus seed. Supported-version obligations remain; a separate 900-second run for every conceivable combination of release, mode and driver was an agent-created matrix, not a user requirement.

Keep the comparison direct, using the existing SQL Faker, database and Testcontainers APIs. Do not restore the rejected observation/fixture/lifecycle framework, a dedicated Diff suite, or per-input catalog/state synchronization. Keep the generated history available for reproducing state-dependent failures.

Eris: execute generated semantic values after analysis

Eris generators for all semantic types
    -> composed, meaning-bearing concrete analysis results
    -> MemoryDB's post-analysis phases
    -> successful operation

Every meaning-bearing, structured model type in sql-semantics and sql-semantics-mysql needs a corresponding real Eris generator, including nested values, interfaces and enums in the model. Generators must be used in executable compositions. Merely constructing objects, checking their PHP classes, or referencing generator classes does not establish correct execution.

PHPStan must guarantee the model-to-generator mapping. Discover the model inventory independently of the generator inventory so that a missing generator cannot disappear from the checked set. Keep the requested configurable class-unused rule, with its selected classes configured in NEON. Static existence and reachability checks do not prove that all value domains are exercised.

Start execution with a complete concrete result of SQL Semantics analysis. MemoryDB must consume its semantic information through the phases after analysis. Do not reconstruct SQL and analyze it again, or recover missing meaning from retained SQL text or parser ASTs. Typed construction/publication in generators must produce the complete semantic input needed by those phases.

SQL errors are not generally acceptable in PBT. An error caused by runtime state, such as a referenced table not existing, may be allowed. This is not a permission to catch every SqlError: non-state-dependent SQL errors must fail, as must representation errors and implementation failures. If generated prerequisites satisfy the statement's state dependencies, the generated sequence must complete successfully.

Generate dependent inputs through Eris composition, for example a table definition followed by an insertion for that definition. Preserve those relationships during standard Eris shrinking. The then() callback executes the generated inputs; it must not reconstruct their dependencies. Fixed expected error codes, account snapshots, source-text markers and scope-cleanup assertions can belong to other tests, but they do not define this execution property.

Property units are the concrete types returned by analyze(), not each small nested type and not one aggregate search for all statements. Use this structure:

Decisions needed from the user

  1. Statements whose analysis records a parse-level refusal (ParseFailure) or a structural problem other than a missing object are not generated for execution (Tests\Support\Analysis::accepted). MemoryDB turns those problems into errors that do not depend on database state, so the property cannot hold for them. The alternative is a second property that checks the mapped error.
  2. Server capabilities are treated as database state: debug-only statements (SHOW PROCEDURE CODE, SHOW PARSE_TREE), XA START/END options the server never supports, components and plugins that are not installed, replication that is not configured.
  3. Server refusals that depend on the value written, not on state, remain failures: for example Incorrect usage/placement of 'SQL_CACHE', Variable 'MYSQL_ERRNO' can't be set to the value of 'NULL', invalid SRS definitions. Many were removed by generating valid values (temporal literals, SQLSTATEs, charsets, collations, system variables, EXPLAIN formats, JSON attributes, JSON paths, replication filter patterns, component URNs, password hashes); the remaining 60 are listed in build/property-nonstate.txt.
  4. Operands typed only at run time (parameter markers, user variables) reach MemoryDB's compiler with no resolved type and raise a LogicException instead of executing or failing as the server would. This is a MemoryDB defect class, not a generator issue.
  5. Tests\Support is a namespace prefix the toolkit lint forbids; the helpers (Analysis, Operands, Embedding, Bindings, Columns) live there because the rename was declined. A permitted name is needed.
  6. Exact comparison of SHOW STATUS cannot pass without modelling InnoDB handler statistics and the image's provisioning connections; the memo's rule leaves only the two options above.
