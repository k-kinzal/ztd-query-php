Laravel feasibility experiment

This is a reproducible design experiment. It does not enable Query Builder or Eloquent support in sql-catalog. See the findings and proposed design before interpreting the results.

Run

Use PHP 8.3+ with PDO SQLite. The package itself still supports PHP 8.1; the isolated oracle uses Illuminate Database 13.33.0, pinned in runtime/composer.lock. Its dependencies are not added to the library.

From packages/sql-catalog:

composer install
composer install --working-dir=experiments/laravel/runtime
bash experiments/laravel/run.sh

The runner disables Xdebug and gives the vendor analyses a 1 GiB memory limit. It writes full catalogs, oracle SQL/bindings, rejected cases and comparisons to the ignored results/ directory. observed.json records a reviewed run; times and memory are observations, not assertions. Each analysis runs in a fresh PHP process. The static analyzer and the model prototype do not load Laravel's autoload file or execute application source.

oracle.php intentionally executes only the checked-in fixture bodies in cases.php, using the same source wrapper as the static analyses. It runs both values of the fixture's Boolean parameter. It captures SQL and bindings at the connection boundary with beforeExecuting() while pretend() prevents query execution. Each dialect uses Laravel's own connection and grammar classes. The PDO object is an in-memory SQLite connection used only for quoting by Laravel's pretend log; that interpolated log is not used as the oracle. No MySQL or PostgreSQL server is contacted. All cases also execute against fresh, seeded SQLite databases, which exposes eager-loading queries pretend cannot see. These observations cover the fixtures' scalar bindings, not every PDO binding conversion Laravel supports.

The Laravel feasibility experiment job in the package workflow runs the same commands on PHP 8.3 and uploads all result files as a workflow artifact.

What each file measures

FilePurpose
cases.php, models.phpRaw SQL control, Query Builder operations, mutable/aliased builders, branches, closures, Eloquent scopes, soft deletion and relations
oracle.phpLaravel's SQL and binding arrays in MySQL, PostgreSQL and SQLite grammars, plus actual SQLite executions
analyze.phpExisting analyzer with application source alone, all installed vendor PHP with the Laravel extension, or all vendor PHP with PDO sinks at two budgets
probes.phpMinimal framework-free examples that distinguish ordinary wrappers from missing instance-state, callback and dynamic-dispatch semantics
ChainModel.php, mappings.phpBounded source-only prototype: configured method effects update query state before an execution method compiles it
model.phpApplies that prototype to the same case source, reporting unsupported input explicitly
compare.phpCompares SQL bytes, binding values and their order; checks the raw control, parse errors, conservative rejection and the eager-loading oracle

The prototype accepts one fluent chain with literal arguments. It does not use the analyzer's backward slicer or implement general PHP flow analysis. Its only configured Eloquent model is the fixture PlainUser, with a known table and no timestamps or scopes. This is an explicit assumption, not inferred model metadata. Additional statements, aliases, branches, callbacks, unconfigured models and unknown methods are rejected. In a production implementation those states must travel through the existing dependency analysis.

The incomplete-model status in the prototype's result is an experimental abstention, not a new catalog entry produced by the library. The raw SQL control is also outside this prototype; the existing extension handles it.

compare.php exits unsuccessfully on an exact-query mismatch, source parse errors or a violation of the experiment's controls. It deliberately does not assert that vendor tracing must keep failing. Change the corpus and controls together when extending the experiment, and review any newly supported effect.

Boundaries of the evidence

The 21 cases are diagnostic examples, not a representative application sample. A match establishes agreement for that input, dialect and pinned version; it does not estimate Laravel-wide precision or recall. Unknown cases are counted as unsupported, not correct. No complete generic object-state analyzer or full Laravel model has been implemented for this comparison. Other Laravel releases, custom grammars, prefixes, macros, model events, casts and dynamic values need their own experiments and contract tests before support is claimed.

The library's verification contracts remain the acceptance criteria for a production change. Differential checks against Laravel would supplement those contracts, rather than replace them with corpus scores.
