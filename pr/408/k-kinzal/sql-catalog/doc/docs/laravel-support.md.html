Investigating Query Builder and Eloquent support

Status: design experiment; production support is not implemented.

The evidence supports testing a combination of shared object-state analysis and framework-specific call models next. Merely adding vendor source or increasing the backward search budget does not recover Laravel-built queries today. A mapping from a method name directly to one SQL template is also insufficient: query state, connection grammar and model effects determine the statement.

This is a proposal for discussion, not a settled extension API. The experiment is reproducible and isolated from the library's dependencies.

What was compared

The run uses the analyzer at monorepo commit 774e55ba22, PHP 8.5.8, nikic/php-parser 5.9.0, and Illuminate Database 13.33.0 with locked dependencies. It tests 21 source examples: one raw-SQL control and 20 Query Builder/Eloquent examples. The same fixture bodies are read by the analyzer and executed by Laravel's oracle. Both outcomes of the fixture's branch are observed.

The vendor runs explicitly include every installed vendor PHP file, despite the normal scanner excluding vendor directories by default. There are 1,978 source files in those runs, including the 22 application/model files. None fails to parse. The PDO runs enable only pdo, so the existing Laravel extension's framework boundary does not explain their failure by itself.

The default budget is 20,000 steps, call depth 4 and 2 loop passes. The larger budget is 100,000 steps, depth 16 and 4 loop passes. Every run starts in a fresh PHP process without loading Laravel classes.

SQLite execution independently agrees with the model on these cases. This is feasibility evidence for modelling those effects, not a claim of 100% precision on Laravel applications.

Why reaching PDO is not enough yet

Laravel does ultimately call PDO. Its query text, however, is generated from an object graph before it reaches that call:

application call
  -> facade / Eloquent forwarding
  -> mutable Builder state and model scopes
  -> connection-specific Grammar
  -> Connection::select / insert / update / delete
  -> callbacks and PDO receiver resolution
  -> PDO::prepare / execute

In the actual vendor catalog, Connection::select()'s $this->getPdoForSelect($useReadPdo)->prepare($query) is unmatched: the receiver cannot be identified. PDO properties/returns are commonly documented with PHPDoc and can hold closures; the current type index reads native declaration types. Resolving that receiver would expose further dependencies, not settle the Builder's SQL.

The framework-free probes isolate four additional gaps. Each probe ultimately issues select * from users at runtime; the first two resolve statically, and the remaining four stay incomplete-model at both budgets:

These correspond to real Laravel paths. Query Builder's toSql() and runSelect() read accumulated state and call the connection. Grammar's compileComponents() uses variable property and method names. Eloquent's __call() and __callStatic() forward calls. The PDO path in Connection passes SQL through closures.

A generic source-based solution is possible in principle. It requires extending these PHP semantics, maintaining instance/call context through them, and then measuring whether budgets still permit useful results. This experiment has not implemented or ruled out that solution. It establishes that reading more files and increasing depth alone are insufficient in the current analyzer.

What a configurable mapping must express

A useful mapping describes effects on a state, for example:

Connection::table(table)       -> create QueryState(table, connection)
QueryBuilder::where(column, v) -> append predicate and binding to that state
QueryBuilder::get()            -> compile the state as a SELECT

The prototype implements a small version of these transitions in mappings.php and ChainModel.php, without loading Laravel. Even this subset needs behavior, not just string substitution: select() replaces selected columns; first() sets a limit; an update's values must precede its WHERE bindings; identifier quoting depends on the connection grammar.

Several oracle results show where a simple method-to-SQL table would be wrong:

  • ScopedUser::where('active', 1)->get() also adds tenant_id = ?, with bindings [1, 7] from the global scope.
  • SoftUser::where('active', 1)->get() also adds users.deleted_at is null.
  • upsert() sorts its insert columns/bindings, then produces MySQL's on duplicate key update or PostgreSQL/SQLite's on conflict syntax.
  • PlainUser::with('posts')->get() produces only the parent query in pretend mode, but two queries with seeded SQLite: a users query and a posts query constrained by the retrieved user IDs. A toSql() snapshot or pretend log alone would give an incomplete oracle for that operation.

Custom macros, scopes, builders and grammars can change the effect of a call. Matching the method's spelling alone must never certify the reconstructed SQL.

Proposed fit with the existing analysis

  1. Keep the current derivation procedure. Discover terminal calls first, trace dependencies backward, bind callers and run retained steps per alternative. SQL, binding values, provenance, correlations and budget limits continue through the existing catalog/reporters.
  2. Extend shared state tracking. Track object identity, aliases, cloning, mutations without assignment and callback effects. Keep path states separate; a branch's predicates and bindings must stay together. Both source tracing and framework call models benefit from this work.
  3. Describe framework call effects at the extension boundary. Add optional factory, mutation and terminal-call descriptions alongside raw SinkSpec declarations. Keep semantic evaluators in the Analysis layer and abstract state in Evaluation, respecting the existing dependency directions. Existing extensions should not be forced to implement Builder APIs.
  4. Model Laravel's framework behavior explicitly. Use the known connection grammar and model metadata when compiling statements. Application helper and scope bodies should still be analysed where the shared semantics support them. Unmodelled overrides, global scopes, callbacks and relation effects must keep the search open; ignoring one cannot produce resolved SQL.
  5. Allow zero or multiple statements per terminal. Eager loading, pagination and compound writes cannot be represented as a mandatory one-call/one-SQL mapping. Relation data may leave explicit gaps or further query shapes.
  6. Verify effects against pinned Laravel releases. Differential tests compare SQL and ordered bindings. Contract tests cover discovery, dependencies, correspondence and honest completion, especially on unsupported input and exhausted budgets. Executed seeded fixtures supplement pretend where query issuance depends on retrieved data.

Start by proving state tracking on assignment-free mutation, aliases, branches and helper/callback boundaries, then integrate a small set of Laravel effects through that same path. Do not promote this experiment's literal-chain parser to a second application analyzer.

The public configuration shape, initial Eloquent coverage and supported Laravel versions remain decisions for discussion. A PHP effect-provider interface with small declarative call descriptions seems more suitable than a large SQL-template configuration language, but this experiment does not settle that API. A generic vendor-tracing path remains an option if broader PHP analysis is a project goal.
