# Compatibility

mysql-memory aims to answer every statement as the emulated MySQL release answers it, as a client observes the answer. This document explains what that covers, how it is checked, what is emulated, and where the emulator is known to differ. Every difference listed here can be reproduced with the statement given or described.

## What "the same answer" means

For each statement, a client observes:

- for a statement that returns rows: the result columns (name, table, original table and database, type code, length, decimals, flags, collation) and the rows, each value as the text the server sends;
- for any other statement: the affected-row count, the last insert id and the information text (`Records: 2  Duplicates: 0  Warnings: 0`);
- for a statement that fails: the error number, the SQLSTATE and the message;
- the warnings and notes `SHOW WARNINGS` lists afterwards, and the rows of every table afterwards.

These observations define the compatibility target. The implementation remains incomplete, including some cases where the server and emulator choose different errors or warnings. A passing campaign covers its sampled statements only.

## How it is checked

- **Specification.** Each rule is written from the MySQL reference manual, which the code cites. Where the manual is silent, the rule was read from a live server, and the code says so ("verified on a live 8.4 server").
- **Unit tests** cover each rule.
- **Differential fuzzing** (`fuzz/`) generates statements from the official MySQL grammar with SQL Faker and compares them on real MySQL and mysql-memory from the same fixtures. It records every PDO result set, the column metadata PDO exposes, affected rows, insert ids, errors, warnings and table contents. It does not yet record OK-packet information text or column metadata absent from PDO. The fixture fixes `timestamp`; reference observations that differ between two runs are skipped and counted separately, not counted as matches. A report retains all differing SQL and generation inputs for replay. mysql-memory starts with the real server's global variables so host names, paths and identities agree. The README explains [how to run it and interpret the exit status](../README.md#how-correctness-is-checked).

## Releases

The `version` argument selects one of the MySQL grammar releases of SQL Parser: `5.6.51`, `5.7.44`, `8.0.44`, `8.1.0`, `8.2.0`, `8.3.0`, `8.4.7`, `9.0.1` or `9.1.0`. It decides:

- the grammar and keywords a statement is parsed with, including version comments (`/*!80000 ... */`);
- the system variables that exist and their defaults, such as the default `sql_mode`;
- what `VERSION()` and `@@version` report.

The rest of the behavior is modeled on MySQL 8.4: the error messages, the default character set and collation (`utf8mb4`, `utf8mb4_0900_ai_ci`), the text of `SHOW CREATE TABLE`, the accounts of a new installation (except in 5.6 and 5.7, see [Accounts](#accounts)), and the storage engines, plugins and privileges `SHOW` lists. Releases of the 8.x and 9.x series share most of it. MySQL 5.6 and 5.7 differ in many of these points, so expect differences there: for example, 5.7 names a duplicate key `'PRIMARY'` where mysql-memory names it `'t.PRIMARY'`, and writes `int(11)` where mysql-memory writes `int`.

## Connecting

- The server speaks the client/server protocol 4.1: the handshake with `mysql_native_password`, text queries, multiple statements and multiple results in one query, and the binary protocol of server-side prepared statements, including long data.
- Parse-time deprecations are reported when a statement is prepared and are not repeated by its executions. A wire PREPARE starts a fresh diagnostics area in MySQL 5.7 and later. MySQL 5.6 retains previous conditions when preparation opens no table. Preparation failures remain available through SHOW WARNINGS, and the preparation response reports its warning count.
- Prepared executions retain derived parameter types from MySQL 8.0.22 onward and count automatic repreparation for type changes. Direct arithmetic and comparison markers inherit their other operand's type; CAST performs its own conversion. Other parameter contexts still start as VARCHAR and do not yet cover every inference rule. SQL PREPARE on MySQL 5.x retains its legacy string result metadata while numeric expressions use the bound numeric kind.
- Any user name and password are accepted. The session belongs to the user name given, at the host the client connects from (or the `clientHost` of the server); `CURRENT_USER()` reports the user at `%`.
- `COM_INIT_DB`, `COM_PING`, `COM_RESET_CONNECTION` and `COM_QUIT` are answered.
- TLS, compression and `CLIENT_DEPRECATE_EOF` are not offered. `CLIENT_FOUND_ROWS` (`PDO::MYSQL_ATTR_FOUND_ROWS`) makes UPDATE report matched rows and unchanged ON DUPLICATE KEY UPDATE rows count as one. ROW_COUNT() uses the same count. Resetting the connection preserves the negotiated flag.
- Packets of 16 MiB or more, which the protocol splits, are not supported.

## Queries

- MySQL 5.6 and 5.7 derived tables exclude outer query tables, while retaining routine parameters, local variables and trigger rows. In newer releases, outer-column dependencies cross non-lateral derived tables without counting the containing FROM clause as a visible scope. Routine integer variables and unreduced integer scalar subqueries keep their direct result type and use a separate integer storage field when materialized. MySQL 5.6 derived tables always materialize; later releases honor `derived_merge` and retain assignments and dependent selected queries behind a materialization boundary. Unreduced membership predicates retain nullable result metadata even when their input columns are declared NOT NULL.
- Query blocks with every clause: `FROM`, `WHERE`, `GROUP BY` with `WITH ROLLUP` and `GROUPING()`, `HAVING`, `DISTINCT`, `ORDER BY` (by expression, alias or position), `LIMIT` and `OFFSET`, `SQL_CALC_FOUND_ROWS`, `FOR UPDATE` and `FOR SHARE`.
- Aggregate inputs are read when a result row is requested. A constant false `HAVING`, or `LIMIT 0` without an offset, skips aggregate arguments and their warnings or assignments. A positive offset still consumes input with `LIMIT 0`. These evaluation effects are verified on MySQL 8.0, 8.4 and 9.1.
- Ordered results spanning independently varying joined tables retain column identities but lose index flags after buffering. A unique lookup dependent on the first ordered table, a constant table and LIMIT 0 preserve those flags. Other optimizer-dependent buffering choices remain incomplete.
- Joins: comma, `INNER`, `CROSS`, `LEFT`, `RIGHT`, `NATURAL`, `USING`, `STRAIGHT_JOIN`; derived tables, including `LATERAL`; index hints are checked (an unavailable index is error 1176, a view has none) and determine whether an ordered DISTINCT result retains index-backed field metadata. Row access still uses table scans. The indexes of the tables of `information_schema`, `mysql` and `performance_schema` are not checked.
- Common table expressions, including recursive ones; `UNION`, `INTERSECT` and `EXCEPT` with `ALL` and `DISTINCT`; `VALUES ROW(...)` and `TABLE t`.
- In MySQL 8.0 and later, an unsorted `UNION` with `LIMIT` stops evaluating operand expressions after the required rows, including the offset. `SQL_CALC_FOUND_ROWS` and global sorting consume the remaining input. A `UNION DISTINCT` prefix followed by `UNION ALL` is materialized first, including when the outer limit is zero; assignments in that prefix still run.
- Scalar subqueries and `IN`, `NOT IN`, `EXISTS`, `ANY`, `SOME`, `ALL` predicates, correlated or not. Row constructors also support `IN`, `NOT IN` and their `= ANY` / `<> ALL` equivalents against multi-column subqueries, including NULL-aware comparisons and empty results. Single-row, multi-column subqueries can be compared with row constructors or other row subqueries and used as membership operands. More than one result row raises error 1242. Ordinary comparison with an empty row subquery yields NULL. Membership and quantified subqueries reject `LIMIT` in their query blocks, including set-operation branches, while permitting limits inside derived tables and CTE definitions.
- Subquery result metadata follows the query form and release. From MySQL 8.0, a tableless row or aggregate subquery with a known true integer filter retains its selected expressions' NULL attributes; a false or runtime filter keeps the nullable subquery result. MySQL 5.6 and 5.7 keep a filtered unreduced subquery nullable even when its condition is known true. MySQL 5.6 reports unfiltered tableless row subqueries and tableless UNION rows as nonnullable, including rows whose columns contain NULL; the reported attribute does not change their values.
- Null-safe comparison of empty row subqueries depends on the query form and release; some empty queries compare as rows of NULLs, while others remain distinct. Independent projection expressions are read lazily. Their warnings and assignments match the tested forms on MySQL 8.0 and later. MySQL 5.6 and 5.7 retain resolved constant sources and their warning counts within a statement, separately from comparison values cleared on repeated reads. Typed conversions can still inspect those retained sources. Modern releases evaluate the expressions on each comparison. Legacy runtime projections also retain their first source. MySQL 5.6 distinguishes direct columns from computed expressions. Integer user variables retain their source during NULL inspection on both legacy releases; integer assignments do so on MySQL 5.6, while MySQL 5.7 clears the first assignment comparison slot. MySQL 5.6 constant DATE projections retain their first evaluation and warnings separately from the initial NULL state read by a comparison. On both legacy releases, repeated comparisons of a constant DATE with a date or string clear the first comparison slot, while numeric conversions and later output positions retain the value. Other legacy temporal state remains incomplete.
- Aggregate projections retain their initial values before input is read, or their computed values after HAVING or OFFSET discards an aggregate row. Rank windows retain their initial state or their last computed output. Value windows distinguish initial NULL inspection from argument evaluation in empty tableless subqueries, and retain computed slots after OFFSET discards every row. WHERE and HAVING effects precede an exhausted tableless offset; skipped window arguments remain unevaluated. Unread table fields used by value windows, and empty aggregate windows, still need further handling. Parent expressions use logical window types. Temporary-column conversion applies to window-dependent result columns and derived tables; scalar subqueries retain the logical types.
- Set operations keep result fields separately from their input expressions. MySQL 5.6 and 5.7 unordered UNION ALL leaves those fields initialized even when OFFSET consumes rows. MySQL 5.7 sorting retains the last consumed row and skips unordered input entirely for LIMIT 0 even with a positive OFFSET. MySQL 5.6 set-field initialization and sorted or distinct empty results remain incomplete. Other set paths retain rows discarded by set filtering, sorting or OFFSET. MySQL 9.1 makes a bounded UNION's nonnullable fields unavailable to empty-row comparison when an operand is an unbounded tableless block with no filter or a resolved true filter. Local bounds, HAVING, table references and runtime filters retain that operand's buffered path. Preparation-time warnings and assignments in these filters still need work.
- A sole base table retains its column fields across reads and successful single-table writes, with separate handles for each prepared occurrence and connection. Empty row comparisons read those fields without inventing an output row. Missing integer primary-key lookups expose an absent row within that query and retain nullable NULL bits for later statements; sorted reads retain the last row consumed. FLUSH discards persistent handles while keeping temporary ones. Legacy retained-table behavior, joined and locking reads, multi-table writes, stored-program handles and some buffered aggregate forms remain incomplete.
- On MySQL 8.0 and later, scalar and row subqueries that call per-read functions such as `RAND`, read user variables or assign session values are reevaluated for each outer row. Uncorrelated materialized derived tables and common tables retain their rows for the statement, including random values; merged and correlated inputs remain eligible for reevaluation. Retained selected subqueries with per-call effects or session-variable reads also force materialization, so joining the derived rows repeatedly reuses their values. MySQL 5.6 retains independent row-subquery variable reads while still reevaluating random calls, assignments and column correlations.
- MySQL 5.6 and 5.7 materialize unreduced positive `IN` and `= ANY` results as full-width signed BIGINT columns. Their direct scalar result can still report width one; arithmetic over the temporary column uses its stored width.
- Row membership evaluates its left operand before searching candidate rows and caches independent results determined by an integer primary key. MySQL 5.6 rechecks a satisfied cached condition for each outer row, retaining its repeated conversion warnings. MySQL can evaluate operands repeatedly while preparing and executing its chosen subquery plan, so warning counts still differ for expressions such as `SELECT (CAST('x' AS UNSIGNED), 1) IN (SELECT 0, 1)`. Value comparison does not establish equivalence of those diagnostics.
- `SELECT ... INTO @variables`.
- `TABLESAMPLE` is checked as the server checks it without a secondary engine: errors 6033 for `UPDATE` and `DELETE`, 6108 for a table that is not a base table, 6107 for a percentage outside 0 to 100, and 3889 otherwise.
- The `ONLY_FULL_GROUP_BY` check (error 1055) with the functional dependencies the server recognizes.
- Result column names, including the names of unaliased expressions (`SELECT 1+1` names its column `1+1`), and the column metadata the server sends, which depends on whether a column is read from a base table, a view, a derived table or a temporary table.

- Window functions, in MySQL 8.0 and later: `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `PERCENT_RANK`, `CUME_DIST`, `NTILE`, `LAG`, `LEAD`, `FIRST_VALUE`, `LAST_VALUE`, `NTH_VALUE`, and the aggregates `SUM`, `AVG`, `COUNT`, `MIN`, `MAX`, the bit aggregates and the statistical ones with `OVER`. Windows have `PARTITION BY`, `ORDER BY` and `ROWS` or `RANGE` frames, including `INTERVAL` offsets over dates and times; named windows of the `WINDOW` clause can refine one another. Windows are computed after `HAVING` and before `DISTINCT`, `ORDER BY` and `LIMIT`, and over the rows of `GROUP BY`. The rows leave in the order of the last window that sorts, and a single-table query whose windows do not sort applies its `ORDER BY` before them, as the server does. The server's errors are raised in its order of checks: windows used where they are not allowed (3593, 3594), refinements of named windows (3579 to 3583), positions in `PARTITION BY` or `ORDER BY` (3592), nested windows (3595), frames (3586 to 3590, 3596), the arguments of `NTILE`, `LEAD`, `LAG` and `NTH_VALUE` (1210), and the forms the server does not support (`IGNORE NULLS`, `FROM LAST`, `GROUPS`, `EXCLUDE`, `DISTINCT` and `GROUP_CONCAT` over a window, 1235). The result columns of `MIN`, `MAX`, `FIRST_VALUE`, `LAST_VALUE`, `NTH_VALUE`, `LEAD` and `LAG` distinguish direct evaluation from temporary-column materialization. Constant and immediately empty queries retain the direct type; a temporal direct result uses the connection character set. Materialized results carry their stored widths, decimals and BLOB flags, including through transparent expression wrappers. `SHOW CREATE VIEW` writes the windows of a view as the server stores them.

- `JSON_TABLE` in MySQL 8.0 and later, as a table function in `FROM`: its document may read the columns of the tables before it (`FROM t, JSON_TABLE(t.doc, ...)`, `LEFT JOIN JSON_TABLE(...) ON TRUE`) and of outer queries. Every column kind is evaluated (`FOR ORDINALITY`, `PATH`, `EXISTS PATH`, sibling and nested `NESTED PATH`s), with `ON EMPTY` and `ON ERROR` (`NULL`, `DEFAULT 'json'`, `ERROR` with errors 3665, 3666, 3669, 3155 and 3156, and the deprecation warning for `ON ERROR` written first), and the columns take their declared types as the server reports them. Values are converted into the column types exactly; the conversions of `BIT`, `ENUM` and `SET` columns, and of some strings into `TIME`, differ, and the notes and deprecation warnings the server adds while storing a value are not raised.

Not supported: full-text search (`MATCH ... AGAINST`) and the partitions of a table partitioned by `KEY` (`FROM t PARTITION (p0)` fails with error 1235; the other methods are supported).

### Optimizer hints

Hint comments (`/*+ ... */`) right after `SELECT`, `INSERT`, `REPLACE`, `UPDATE` and `DELETE` are read as the server reads them, in MySQL 5.7 (its smaller set of hints) and later; in MySQL 5.6 they are ordinary comments. Every hint of the manual is accepted, with the server's warnings in the server's order:

- a problem in the comment is warning 1064 (`Optimizer hint syntax error`, `Unsupported MAX_EXECUTION_TIME`), and the hints before it still count;
- a hint that repeats or contradicts an earlier one is warning 3126, a query block name no block has is 3127, a table, an index or a variable the hint names that does not exist is 3128, `MAX_EXECUTION_TIME` outside the first block of a `SELECT` statement is 3125, `RESOURCE_GROUP` outside block 1 is 3515, `SET_VAR` of a variable that does not take the hint is 3637, and an unknown resource group is 3651;
- query blocks are numbered and named (`select#N`, `QB_NAME`) as the server numbers them, a common table expression once per reference.

`SET_VAR` sets the session value of its variable for the statement, with the checks and warnings of `SET`, and restores it when the statement ends, also when it fails; `div_precision_increment` and `group_concat_max_len` also type the statement. A prepared statement raises the hint warnings when it is prepared, and only the `SET_VAR` value warnings when it runs. `SHOW CREATE VIEW` writes the `INDEX`, `JOIN_INDEX`, `GROUP_INDEX` and `ORDER_INDEX` hints a view keeps, as the server does.

The hints change no result: join order, index, join buffering, merge and subquery strategy hints are checked only, `MAX_EXECUTION_TIME` sets no timer, and `RESOURCE_GROUP` binds no thread. Known differences: the hint warnings of a statement of a stored procedure are raised when it runs, not also when the procedure is created; the hints of a stored function or a trigger are ignored without a warning, where the server warns about unresolved names at the first call of a function; a syntax problem in a common table expression warns once, not again for each reference; a deprecation warning written after the hint comment of a subquery comes before its syntax warning; `EXPLAIN` writes no note 1003 with the hints.

A consistent single-table read with literal integer equalities covering its primary key restricts candidate rows before evaluating the remaining row predicates. Unmatched rows therefore do not contribute conversion warnings or variable assignments. MySQL 5.6 and 5.7 re-evaluate a passing predicate of a constant primary-key row, including its warnings and assignments; a rejected first evaluation and LIMIT 0 do not trigger that second read. Partial keys, other coercions, index hints and locking reads retain the existing scan behavior.

Without `ORDER BY`, a table is read in the order of its clustered index (the primary key, else the first unique key over `NOT NULL` columns, else insertion order), as an InnoDB table scan reads it. The server may choose another access path and return rows in another order; only `ORDER BY` fixes the order on both.

In MySQL 8.0 and later, `GROUP BY` without `ORDER BY` returns the groups in the order their first rows are read, as the server's temporary table of groups does. The groups come sorted by their expressions when the expressions are the leading columns of a key of the table, in key order, with `WITH ROLLUP`, and with `GROUP_CONCAT`, `JSON_ARRAYAGG`, `JSON_OBJECTAGG` or an aggregate over `DISTINCT` other than `MIN` and `MAX`; MySQL 5.6 and 5.7 also sort ordinary groups, while DISTINCT over hashed groups can preserve arrival order before duplicate removal. The server can choose another plan, such as reading a covering secondary index, and return the groups in another order.

## Expressions

- Literals of every form: numbers, strings with character set introducers, hexadecimal and bit values, `DATE`, `TIME` and `TIMESTAMP` literals, ODBC escapes, `TRUE`, `FALSE`, `NULL`.
- Arithmetic over integers, exact decimals (with `div_precision_increment`) and doubles, with the server's overflow errors (`BIGINT value is out of range`), division by zero (NULL, with a warning or an error as `sql_mode` says), `DIV`, `MOD`, `%`, bit operators.
- Comparison with the server's conversions: a string compared with a number is read as a number, with the warning `Truncated incorrect DOUBLE value`; `=`, `<=>`, `<>`, `<`, `IS [NOT] NULL`, `IS [NOT] TRUE`, `BETWEEN`, `IN`, `LIKE` with `ESCAPE`, `REGEXP`, `SOUNDS LIKE`, row comparisons.
- Collations: the collation of each comparison is decided by coercibility as the server decides it (error 1267 for an illegal mix). Untailored Unicode 4.0, Unicode 5.2, Unicode 9.0 and Unicode general_ci collations use the weights checked by WEIGHT_STRING for comparisons, grouping and uniqueness. Other Unicode collations use ICU at the strength of the collation. For example, `'é' = 'e'` is true under `utf8mb4_0900_ai_ci` and false under `utf8mb4_0900_as_cs`; `PAD SPACE` and `NO PAD` collations treat trailing spaces as the server does. For untailored Unicode 4.0 and 5.2, temporary grouping and DISTINCT can distinguish a space before a trailing ignorable character from a trailing space alone. Unindexed string equijoins retain this hash-key distinction when their maximum key capacity exceeds 1024 bytes. Ordinary comparisons, indexed lookups, sort deduplication and `COUNT(DISTINCT)` compare their weights with padding. DISTINCT preserves the observed small-table index-grouping crossover after index maintenance; physical page costs, large-table sampling and automatic statistics recalculation remain unmodeled.
- `CASE`, `CAST` and `CONVERT` to every target type, `CONVERT ... USING`, `BINARY`, `COLLATE`.
- Date arithmetic: `DATE_ADD`, `DATE_SUB`, `+ INTERVAL`, `- INTERVAL` with every unit, and `EXTRACT`.
- JSON: JSON columns store the normalized document (`'{"b":1,"a":2}'` reads back as `{"a": 2, "b": 1}`), and JSON values keep the types the server keeps in its binary format: a decimal (`JSON_OBJECT('p', 5.00)` keeps `5.00`), an unsigned integer, a date, a time, a datetime, a timestamp and an opaque value (`"base64:type15:..."`) keep their type through functions, columns and `JSON_TYPE`. `CAST(... AS JSON)` normalizes a string as a JSON column does (error 3141 naming `cast_as_json`) and makes other values JSON values of their type. JSON values compare with each other and with SQL values by the server's JSON rules (an SQL string is a JSON string, a predicate a JSON boolean, types ranked from `NULL` to opaque values); `BETWEEN` with JSON compares as the server does, with its warning; `ORDER BY`, `GROUP BY`, `DISTINCT`, `MIN` and `MAX` follow the JSON order, with the warning for sorting arrays and objects. A JSON value read as a number or a date converts by its value with the server's warnings 3155 and 3156, naming the column or function and the row. The `->` and `->>` operators and `MEMBER OF` are evaluated.
- User variables (`@v`, `@v := expr`) and system variables (`@@v`, `@@SESSION.v`, `@@GLOBAL.v`).
- `NOW()`, `CURRENT_TIMESTAMP`, `CURDATE()`, `CURTIME()`, `LOCALTIME`, `LOCALTIMESTAMP`, the `UTC_` clocks and `SYSDATE()`. Every clock of a statement except `SYSDATE()` reads the instant the statement started, in the time zone of the session (`time_zone`). `SET timestamp = n` fixes that instant for the session, as on the server, so a test can pin the clocks, `UNIX_TIMESTAMP()` and `CURRENT_TIMESTAMP` defaults; `SET timestamp = DEFAULT` (or 0) restores the clock.

### Built-in functions

`GROUP_CONCAT` result metadata accounts for direct results, materialized derived
columns and UNION columns separately. Bounds depend on `group_concat_max_len`,
the expression character set and the emulated release. Converting TEXT/BLOB
result metadata from UCS-2 or UTF-16 uses the source character set's minimum
width. MySQL 5.6 string casts preserve the operand's nullable attribute; later
releases report those casts as nullable.

A scalar subquery that reads a TEXT/BLOB column uses the column's
collation-expanded bound. Computed string expressions retain their own bound;
resolved column bindings preserve this distinction through parentheses, stars
and result aliases.

Control functions retain a computed blob's character bound separately from its
reported byte width. Nested `COALESCE`, `IFNULL`, `NULLIF`, `CONCAT` and `HEX`
therefore use the original expression bound. String field types and decimals
follow the release-specific rules, including legacy `NULLIF` and computed
`MIN`/`MAX` results. MySQL 5.6 reports long `CONCAT`, `CONCAT_WS` and `REPLACE`
results as nullable even when their arguments are not nullable.

Temporal `NULLIF` results report string metadata while preserving temporal
conversion during direct evaluation. Once stored in a materialized derived
table, they convert as strings. Legacy numeric `NULLIF` results use LONGLONG or
DOUBLE fields. Arithmetic on fixed-scale FLOAT and DOUBLE values retains its
scale; division adds `div_precision_increment`. MySQL 8.0 YEAR results retain
their integer evaluation and storage behavior despite reporting string fields.
For DECIMAL division, reaching the maximum scale does not stop result precision
from growing by the configured increment.

Computed `CREATE TABLE … SELECT` columns retain whether their default collation
was implicit. `SHOW CREATE TABLE` preserves this distinction through column
copies, `CREATE TABLE … LIKE`, and alterations that keep the column definition.
Fixed-scale FLOAT and DOUBLE results retain their fractional digits in UNION
and stored query results. MySQL 5.6 and 5.7 can store a computed DOUBLE with a
reported width absent from `SHOW CREATE TABLE`; that width survives table copies
and column-preserving alterations, and resets when the type is explicitly changed.

Materialized computed strings longer than 512 characters use BLOB columns.
Their direct result width and the storage capacity read by later expressions
are distinct, including the MySQL 5.6 character-based allocation rule and the
later byte-based rule. `CONCAT`, `CONCAT_WS` and `REPLACE` cap long-blob metadata
at 16 MiB before result character set conversion; this metadata limit is
separate from the execution limit controlled by `max_allowed_packet`.
TEXT/BLOB results of `UNION` and `UNION ALL` retain their storage capacity for
later scalar and derived-table reads, with the separate MySQL 5.6 scalar rule.
Combining further set operands retains the original bounds.
MySQL 5.7 reports unordered `UNION ALL` string columns without temporary-table
attributes when returning the statement directly. Scalar and derived-table
consumers keep the materialized column types.
Temporal `NULLIF` results read through an unreduced scalar subquery use string
numeric conversion. Numeric reads of scalar string results do not emit
truncation warnings; a subquery reduced to its expression keeps that expression's
warnings. Set operations resolve the returned field independently of the
operand's evaluation kind, including temporal strings and BIT fields.
MySQL 5.7 retains the fractional precision of temporal strings in a streamed
`UNION ALL` result; materialized set columns clear that reported precision.
BIT values retain unsigned ordering and distinct keys for grouping, sorting and
unique constraints, including values above the signed 64-bit range. MySQL 5.6 and 5.7
BIT extrema evaluate numerically while reporting BIT fields; storing their
results in derived tables or UNION restores packed BIT values. Selected BIT
sort keys of an ordered DISTINCT result use integer metadata when the chosen
path stores them. Covering indexes and selected non-null unique keys can avoid
that storage; `LIMIT 0` retains the original field metadata. USE, FORCE and IGNORE
INDEX apply their grouping and ordering scopes. Invisible indexes participate
only when `optimizer_switch` enables `use_invisible_indexes`.
`MIN` and `MAX` over TEXT/BLOB columns preserve separate expression and metadata
bounds, including grouped column references, scalar subqueries, and later
`CONCAT` or `HEX` calls.

`UUID()`, `UUID_SHORT()`, `RANDOM_BYTES()` and `ENCRYPT()` without a salt cannot give the server's values: `UUID()` is a version 1 UUID with a node drawn at random for each emulated server, and `UUID_SHORT()` counts from the time the emulated server first answers it instead of the time the server started. `SHA2` is typed as long as its longest digest unless its length is a literal, where the server also sizes it by a constant expression such as `1 + 0`.

`RAND(N)` answers the sequence of the server for each seed: a seed known for the statement starts one sequence that each row advances, any other seed starts one for each row. `RAND()` without a seed draws from PHP's random generator, so its values differ from the server's. A `RAND` of the select list is evaluated for every row before `ORDER BY` and `LIMIT` apply, where the server evaluates it only for the rows it sends, so with those clauses the values can come in another order. `GREATEST` and `LEAST` are evaluated as MySQL 8.0 and later evaluate them; MySQL 5.6 and 5.7 compare numbers with strings and temporal values otherwise, and the emulator does not follow them there, though it reports the type and length of their result as those releases do.

**Time, sleeps and user-level locks.** The emulator never stalls the caller. `SLEEP(n)` answers at once, and the time it would take passes on the clock of the emulated server instead: `SYSDATE()` in the same statement, and `NOW()` and the other clocks of every later statement of every session, read the current time plus all the time sleeps and lock waits have passed so far. User-level locks are shared by the sessions of one `Instance` (or one `Server`), case-insensitive and accent-sensitive, counted when a session takes one again, and released when the session ends: `Session::close()`, the client disconnecting, `COM_RESET_CONNECTION`, or the `Session` object being destroyed. Since one statement runs at a time, a lock another session holds cannot be released while `GET_LOCK()` waits: it answers 0 after letting its timeout pass on the clock, and a negative (endless) timeout answers 0 at once where the server would wait forever. `BENCHMARK(count, expr)` evaluates an expression that assigns no variable, reads no subquery and calls no function such as `RAND()`, `SLEEP()` or `GET_LOCK()` only as often as the warnings it raises still fit the diagnostics area, while counting the identical warnings omitted by that shortcut; any other expression is evaluated `count` times.

**Values that depend on the server.** `ICU_VERSION()` answers the ICU version each release bundles (77.1 for 8.0.44 and 8.4.7, 73.1 for 9.1.0; the values of 8.1, 8.2, 8.3 and 9.0 are not verified). A thread id (`PS_CURRENT_THREAD_ID()`, `PS_THREAD_ID()`) is the connection id plus the number of threads a freshly started server of the release runs before its first client (40 for 8.0.44, 37 for 8.4.7, 36 for 9.1.0), while a long-running server numbers its threads further apart. `ROLES_GRAPHML()` lists the accounts the emulator models: no `healthchecker` account, which some Docker images add; the edges of one grantee are listed together, in the order its first role was granted, where the server lists every edge in the order of the grants.

`NAME_CONST` resolves literal argument restrictions before execution, including NULL names and the rejection of bare boolean values in MySQL 8.0 and later. MySQL 9.1 accepts negated or collated boolean values. Parentheses and unary plus preserve a literal name. Floating and temporal names use their normalized value, including fractional seconds; SQL Semantics and execution share these value-formatting rules.

**Weight strings.** `WEIGHT_STRING` resolves binary result capacity by collation, with distinct legacy sizing. Evaluation supports binary strings, Unicode `_bin` and `general_ci` collations, `utf8mb4_0900_ai_ci`, `utf8mb4_0900_as_ci`, `utf8mb4_0900_as_cs`, the `_unicode_ci` and `_unicode_520_ci` collations, and the single-byte latin1 collations in the sampled weight catalog, including CHAR/BINARY lengths and the four-argument form. The general_ci mapping is identical across all valid BMP code points sampled on MySQL 5.6.51 and 8.4.7. Untailored Unicode 9.0 weights use the public Unicode data, with implicit ideograph and Hangul weights; every Unicode scalar was compared with MySQL 8.0.44, 8.4.7 and 9.1.0. Legacy LEVEL selectors and DESC/REVERSE modifiers are evaluated for supported single-level collations. In MySQL 5.6 and 5.7, Unicode 4.0 and 5.2 length limits count primary weights rather than source characters, including truncation inside expansions. The accent-sensitive variants concatenate secondary and tertiary levels after the primary level, including empty-level separators. Untailored Unicode 5.2 primary weights are regenerated from its public Unicode data; all Unicode scalars and 715 multi-character sequences were compared with MySQL 9.1.0. Its implicit Han ranges and undecomposed Hangul follow observations through SQL. Untailored Unicode 4.0 weights use its public Unicode data; all Unicode scalars match MySQL 8.0.44, 8.4.7 and 9.1.0, and the data's 77 multi-character sequences match 9.1. Supplementary characters share FFFD, and expansions longer than eight elements use implicit weights. Locale tailoring remains unsupported.

**Functions the server keeps for itself.** `CONVERT_CPU_ID_MASK()`, `CONVERT_INTERVAL_TO_USER_INTERVAL()` and the other functions the server reserves for its own views are refused with error 3566 whatever their arguments, as the server refuses them. `LIKE_RANGE_MIN()` and `LIKE_RANGE_MAX()`, which only a debug build of MySQL 5.7 has, do not exist (error 1305), as in a release build. `SOURCE_POS_WAIT()` and `MASTER_POS_WAIT()` without a channel fail with error 3079 from MySQL 8.1 on, as MySQL 8.4 and 9.1 do on a server without replication channels; 8.1 to 8.3 are not verified. In MySQL 5.6 `GTID_SUBTRACT()` of arguments that cannot be NULL is reported NOT NULL by the server and nullable by the emulator. A statement given to `STATEMENT_DIGEST()` or `STATEMENT_DIGEST_TEXT()` is refused for what the parser of the server checks itself (a syntax error, an empty text, a table named without its database while none is chosen); the checks the server makes beyond those while it parses, such as an unknown system variable, an unknown collation or an invalid default value, are not made, and the digest is computed.

**Strings compared with temporal columns.** A constant string compared with a `DATE`, `DATETIME` or `TIMESTAMP` column is read as a value of the column: a string with more text after the value warns (1292) and compares as that value, and a string that holds no value warns and, from MySQL 8.0 on, fails the statement with error 1525 when the comparison is an operator rather than `IN` or `BETWEEN`. A `TIME` column warns about a string that holds no time. Known differences: the error comes when the statement is compiled, after the names of every clause are resolved, where the server raises it as it resolves the comparison; MySQL 5.6 and 5.7 warn once more for a comparison in `WHERE`; a row comparison such as `(e, 1) = ('x', 1)` is not checked.

## Writes

- `INSERT` and `REPLACE` with `VALUES`, `VALUE`, `SET` or a query, with or without a column list; `DEFAULT` and `DEFAULT(col)`; `INSERT IGNORE`; `ON DUPLICATE KEY UPDATE` with `VALUES(col)` or the row alias of `INSERT ... AS alias` and its column aliases (`AS new(x, y)`), and after `INSERT ... SELECT` with the columns of the query; `VALUES(col)` outside `ON DUPLICATE KEY UPDATE` is `NULL` with the server's deprecation warning; `UPDATE ... SET col = DEFAULT`.
- `UPDATE` and `DELETE` of one table with `ORDER BY` and `LIMIT`; multiple-table `UPDATE` and `DELETE`.
- The affected-row count, the last insert id and the information text are the server's: an `INSERT ... ON DUPLICATE KEY UPDATE` counts 2 for a row it updates, a `REPLACE` 2 for a row it replaces, and an `UPDATE` counts the rows it changed, or the rows it matched with CLIENT_FOUND_ROWS. A generated id actually inserted takes precedence in the OK packet; otherwise LAST_INSERT_ID(expr), then the last explicit or updated AUTO_INCREMENT value is used. Explicit values do not change the session's LAST_INSERT_ID(), and an unchanged duplicate alone reports an insert id of zero even with CLIENT_FOUND_ROWS.
- Values are stored as the column type says. Under a non-strict `sql_mode` an integer out of range is clipped, a string too long is cut, and a string that is no number reads as 0, each with the server's warning; under a strict mode each is the server's error. Dates, times, `ENUM`, `SET`, `BIT`, `YEAR`, `DECIMAL` and JSON columns follow the rules of the server, including the zero-date checks of `NO_ZERO_DATE` and `NO_ZERO_IN_DATE`.
- Primary and unique keys are enforced (error 1062, with the key named `table.key` as MySQL 8.0 and later name it). `AUTO_INCREMENT` generates values, honors `NO_AUTO_VALUE_ON_ZERO`, and is reset by `TRUNCATE TABLE`.
- Column defaults: constants, expressions (`DEFAULT (1 + 1)`), expressions that read the other columns of the row (`DEFAULT (b + 1)`, computed in column order from the values the row has so far), `CURRENT_TIMESTAMP` and `ON UPDATE CURRENT_TIMESTAMP`, with the server's refusals (errors 3767 to 3772, 1054 in `'default value expression'`).
- With `explicit_defaults_for_timestamp=OFF`, TIMESTAMP columns without an explicit NULL attribute are NOT NULL. The first TIMESTAMP gains automatic initialization and updating when neither is specified; later nonnullable TIMESTAMP columns default to zero, which `NO_ZERO_DATE` rejects. A nullable first TIMESTAMP still occupies that first position. Assigning NULL to a nonnullable TIMESTAMP under this setting stores the statement's current timestamp; nullable columns retain NULL. These properties survive CREATE TABLE LIKE.
- Generated columns, `VIRTUAL` and `STORED`, are computed on every insert and update from the columns before them, stored as the column type says with the server's warnings and errors, and can be indexed. A value written into one is refused (error 3105) unless it is `DEFAULT`. The expressions are refused as the server refuses them: nondeterministic functions (3763), subqueries (3102), variables (3772), later generated columns (3107), `AUTO_INCREMENT` columns (3109), aggregates and windows (1111, 3593), a virtual column in the primary key (3106), and the attributes a generated column cannot have (1221).
- `CHECK` constraints, named and unnamed, on a column or the table, `ENFORCED` or `NOT ENFORCED`, are evaluated on every insert and update in the order of their names; a condition that is NULL passes, a false one is error 3819, or a warning with `IGNORE`. MySQL 5.6 and 5.7 read them and ignore them, as the server does.
- Foreign keys are checked as InnoDB checks them, row by row: a child row needs a parent row (error 1452), and deleting or changing a referenced parent row is refused (error 1451) unless the key cascades with `CASCADE` or `SET NULL`; `SET DEFAULT`, `RESTRICT` and `NO ACTION` refuse it. Cascades go through further keys and self-referencing tables. `REPLACE` of a referenced row deletes it first. `foreign_key_checks = 0` turns every check and cascade off. With `IGNORE` a refused row is a warning. The messages name the key as the server writes it.
- Partitioned tables place each row in its `RANGE`, `LIST` (with or without `COLUMNS`) or `HASH` (also `LINEAR`) partition, refuse a row no partition holds (error 1526), and read and write only the partitions a statement names (`PARTITION (p0)`, error 1748 for a row outside them).
- A statement that fails changes nothing, even after some of its rows were written.

Not emulated:

- **Deep cascades**: InnoDB's limit of 15 nested cascades (error 3008) is applied without the server's exact accounting.
- **Spatial values**: constructors and spatial casts produce binary geometry values and check component types, ring closure and cast ring direction. `ST_SRID` reads an identifier or changes it without transforming coordinates; it preserves the encoded geometry and validates target registration. Geometry property functions report the type, dimension, emptiness and immediate member count. Empty collections have a NULL dimension, and nested empty collections remain empty. Legacy readers follow their release-specific header checks. Column writes enforce encodings, SRID restrictions and release-specific geometric subtypes. Spatial index declarations and restrictions are checked. Geographic coordinate-range and topological validation remain incomplete. Spatial casts preserve the SRID and reject an unknown SRID.

## Definitions

- `CREATE DATABASE`, `ALTER DATABASE`, `DROP DATABASE`, with character sets and collations.
- `CREATE TABLE` with scalar and spatial column declarations, keys, indexes, defaults, `AUTO_INCREMENT`, invisible columns, table options; `CREATE TABLE ... LIKE`; `CREATE TABLE ... SELECT`; `IF NOT EXISTS`.
- Index visibility is retained by CREATE, ALTER, renaming and table copies, and reported by SHOW CREATE TABLE, SHOW INDEX and INFORMATION_SCHEMA.STATISTICS. An explicit or implicit primary key cannot be invisible. Invisible unique indexes still reject duplicates.
- `ALTER TABLE` with its actions (columns, keys, renames, options), `CREATE INDEX`, `DROP INDEX`, `RENAME TABLE`, `DROP TABLE`, `TRUNCATE TABLE`. An `ALTER TABLE` converts the rows of the table into the new definition, with the warnings or errors of the server, and changes nothing when it fails.
- `SHOW CREATE TABLE` writes the definition as the server writes it.
- The statements that commit implicitly commit an open transaction first.

Differences:

- **Storage engines**: an InnoDB table is transactional, and a table of any other engine (`MyISAM`, `MEMORY`, `CSV`, `ARCHIVE`, ...) is not: see [Transactions](#transactions). Otherwise every engine stores rows as InnoDB does.
- **Temporary tables** belong to the session that creates them: only it sees them, a temporary table hides a base table of its name from it, they end with the session, and `SHOW TABLES` and `INFORMATION_SCHEMA` leave them out. Opening one twice in a statement fails with error 1137, including through multiple references to a CTE that reads it. An unused CTE opens no table; a CTE can also shadow a temporary table of the same name. Write targets open before their query sources, and outer FROM tables before scalar subqueries, so the error names the first opened reference. Inside a stored function or trigger on MySQL 5.6 and 5.7, it names the repeated reference instead. Stored program definitions defer this check until execution; view definitions perform it immediately. `ROLLBACK` warns that creating or dropping a temporary table is not undone (1751, 1752).
- **Foreign keys, `CHECK` constraints and generated columns** are kept with the names the server gives them (`t_ibfk_1`, `t_chk_1`), which follow a renamed table; foreign key and `CHECK` constraint names are unique in a database. `ALTER TABLE` adds, drops and changes them with the server's checks: an existing row that violates a new constraint is refused, a column a constraint or generated column reads cannot be dropped or renamed (1828, 1829, 3959, 3108), an index a foreign key needs cannot be dropped (1553), a referenced table cannot be dropped or truncated (3730, 1701). `SHOW CREATE TABLE` writes them as the server does.
- **Partitioning**: `PARTITION BY` in `CREATE TABLE` and `ALTER TABLE` with the server's checks, `REMOVE PARTITIONING`, and `ADD`, `DROP`, `TRUNCATE` and `COALESCE PARTITION`; the other partition actions fail with error 1235. Rows of a table partitioned by `KEY` are not placed in their partitions (the server's hash is not reproduced).

## Views

`CREATE VIEW`, `CREATE OR REPLACE VIEW`, `ALTER VIEW` and `DROP VIEW` are emulated with `ALGORITHM`, `DEFINER`, `SQL SECURITY` and `WITH CHECK OPTION`; `SHOW CREATE VIEW` writes the view as the server does. A view reads the current definition of its tables, and a view whose tables no longer fit it is invalid (error 1356). `INSERT`, `UPDATE` and `DELETE` through an updatable view write its base table; through a view that is not updatable they fail as on the server. Writing through a view of a view fails with error 1235.

## Stored programs

MySQL 5.7, 8.x and 9.x instances include the public signatures and characteristics of the installed `sys` routines. `SHOW FUNCTION STATUS`, `SHOW PROCEDURE STATUS`, `INFORMATION_SCHEMA.ROUTINES` and `PARAMETERS` list those entries, and routine DDL can alter, drop or replace them. The metadata was observed independently on 5.7.44, 8.0.44, 8.4.7 and 9.1.0. No implementation body is imported: executing an installed routine or showing its source still fails with error 1235, and its `ROUTINE_DEFINITION` is currently NULL. User-created routine bodies execute as described below.

Routine creation and alteration use statement time, including `SET timestamp`; reading a routine displays those instants in the current session time zone. Installation dates default to the time the instance is created. The optional `routineTimestamps` argument of `Instance` and `Server::start()` supplies creation and modification epochs keyed by `FUNCTION:name` or `PROCEDURE:name`; the command line accepts repeated `--routine-time=FUNCTION:name:created:modified` arguments. Differential fixtures import only these initial dates, before any generated statement, and compare every listing field directly. They never import expected result rows or routine bodies.

- `CREATE`, `ALTER` and `DROP` of procedures, functions, triggers and events, with their checks and characteristics, and the `SHOW CREATE`, `SHOW ... STATUS`, `SHOW ... CODE`, `SHOW TRIGGERS` and `SHOW EVENTS` statements that list them.
- Bodies run as the server runs them: `BEGIN ... END` blocks with labels; `DECLARE` of local variables (typed as declared, with `DEFAULT`), conditions, cursors and handlers; `IF`, `CASE`, `LOOP`, `WHILE`, `REPEAT`, `ITERATE`, `LEAVE` and `RETURN`. A statement of a body is resolved when it runs, against the tables of that moment, in the database of the program and under the `sql_mode` the program was created with. A name a parameter or local variable has denotes the variable before a column of the same name, except where a statement names the columns it writes. A value assigned to a variable (`SET`, `SELECT ... INTO`, `FETCH`, `DEFAULT`, `RETURN`) is stored as into a column of the variable's type, so that a warning is the server's error under a strict `sql_mode`.
- Handlers: `CONTINUE` and `EXIT` handlers for error numbers, `SQLSTATE` values, declared conditions, `SQLWARNING`, `NOT FOUND` and `SQLEXCEPTION`, searched from the innermost block outwards with the server's precedence (error number, then `SQLSTATE`, then the classes). A handler runs in the scope of its block, without the handlers of that block, and clears the conditions it handled. `SIGNAL` and `RESIGNAL` (with or without `SQLSTATE` and `SET`), `GET CURRENT` and `GET STACKED DIAGNOSTICS` into local or user variables. An error no handler handles ends the program; the warnings of the last statement are left in the diagnostics area. A handler completes a failing SELECT result with the columns and rows produced before the error. An unhandled error ends that unfinished row stream with an error packet. Unbuffered PDO clients can fetch earlier rows before the error; buffered clients fail while buffering the result. This applies to text queries and native prepared statements.
- Cursors: `OPEN`, `FETCH` (`NOT FOUND` past the last row) and `CLOSE`, with errors 1324 to 1326 and 1328.
- `CALL` binds `IN`, `OUT` and `INOUT` parameters: an `OUT` or `INOUT` argument is a user variable, a variable of the calling program or a column of the `NEW` row of a `BEFORE` trigger (error 1414 otherwise), which receives the value of the parameter. Each query of a procedure, and of the procedures it calls, answers a result set, and the procedure then answers a completion with the rows its last statement affected, which `ROW_COUNT()` reads; the result sets come before an error that ends the procedure. A procedure that calls itself deeper than `max_sp_recursion_depth` fails with error 1456. Each statement of a procedure stands on its own: one that fails does not undo the statements before it.
- Stored functions are called in any expression (select lists, `WHERE`, values written by `INSERT` and `UPDATE`), each call running the function with its arguments stored into the parameter types; the declared `RETURNS` type converts the value, with the call named in its warnings and errors, and a function that ends without `RETURN` fails with error 1321. A function cannot call itself (error 1424), and the conditions of its last statement are added to those of the statement that calls it. A native function of the same name is called instead of an unqualified stored function.
- Triggers fire for each row, `BEFORE` and `AFTER` `INSERT`, `UPDATE` and `DELETE`, in their `FOLLOWS` and `PRECEDES` order, with `NEW` and `OLD` and `SET NEW.col` in `BEFORE` triggers. `INSERT ... ON DUPLICATE KEY UPDATE` fires `BEFORE INSERT` and then the `UPDATE` triggers for a row that conflicts, `REPLACE` the `DELETE` triggers of the rows it replaces, and `UPDATE` its triggers for every matched row, changed or not. A trigger that fails fails its statement, which then changes nothing. A function or trigger that writes a table the statement invoking it uses fails with error 1442.
- Scheduled event bodies are not executed. `event_scheduler` defaults to `ON` in MySQL 8.0 and later, and `OFF` in 5.6 and 5.7. Schedule validation uses the session clock. AT, STARTS and ENDS must fit the release's epoch range after converting the session time zone: from epoch second 1 through 2038-01-19 03:14:07 UTC on MySQL 5.6/5.7, and through 3001-01-18 23:59:59 UTC on modern releases. An out-of-range ENDS reports error 1543. Creating a preserved past event with an explicit disabled status emits no disabling note. ALTER EVENT rejects a past replacement schedule without PRESERVE (1589) before changing the definition; changing completion alone keeps the existing schedule. With the scheduler stopped, an event whose end is after a pinned session clock remains enabled even if it is before the real clock. Real-clock event execution and eventual removal by the daemon remain unimplemented; run an event body explicitly where a test needs its effects.

Not emulated:

- **Metadata of some variables**: a result column that reads a `DATE`, `TIME`, `DATETIME`, `TIMESTAMP` or `JSON` variable of a stored program has the length and decimals of a column of that type, where the server sends the length of its text; a `YEAR` variable is sent as a number.
- **The name of a call in errors**: a value a stored function returns that its type refuses is named after the call as the emulator prints it (`f2(1)`), never after the alias of the select item that holds it.
- **Privileges** of the definer or invoker are not checked, as no privilege is.

## Accounts

The server starts with the accounts of a new installation: `root` at `localhost` and at `%` with every privilege, and the locked system accounts `mysql.infoschema`, `mysql.session` and `mysql.sys`. `CREATE`, `ALTER`, `RENAME` and `DROP USER`, `CREATE` and `DROP ROLE`, `SET PASSWORD`, random passwords, `GRANT` and `REVOKE` of privileges and roles, `SET ROLE`, `SET DEFAULT ROLE`, `SHOW GRANTS` and `SHOW CREATE USER` are emulated, with the server's checks and errors. Random password generation uses the session value of `generated_random_password_length`, including values inherited when the connection starts.

`RETAIN CURRENT PASSWORD` stores the previous primary credential as the secondary, replacing an older secondary; ordinary password changes preserve it. `DISCARD OLD PASSWORD`, an empty new password, or a changed authentication plugin removes it. Retention rejects empty current and new passwords and simultaneous plugin changes. `mysql.user.User_attributes` exposes the retained authentication string under `additional_password`. This models SQL credential state; it does not add wire authentication.

MySQL 5.6 and 5.7 start with the root accounts only, and 5.7 also with `mysql.session` and `mysql.sys`; their accounts use `mysql_native_password`, whose password hash (`*` and the double SHA-1) is the server's, and they know neither roles nor dynamic privileges. There `GRANT` creates the accounts it names, with the password and the TLS and resource options it gives, unless `NO_AUTO_CREATE_USER` (part of the 5.7 default `sql_mode`) requires a password (error 1133); 5.7 warns that this, `IDENTIFIED BY PASSWORD` and changing an account with `GRANT` are deprecated, and that changing `NO_AUTO_CREATE_USER` in `sql_mode` is. In 5.6 `SET PASSWORD = '...'` takes the hash itself and `PASSWORD('...')` hashes a password. `SHOW GRANTS` and `SHOW CREATE USER` write these releases' forms, including the password hash, TLS requirement and limits that 5.6 writes on the global grant.

Manual password expiry is tracked for each connection. A connection that expires its own password must use `ALTER USER` or `SET PASSWORD` to change its credentials before other statements can run (error 1820). Existing connections for the same account retain their previous state, and resetting the account from another connection does not release an already restricted connection. MySQL 5.6's `ALTER USER ... PASSWORD EXPIRE` updates the account without restricting existing connections. Automatic expiry from password age and the wire-protocol negotiation for connecting with an expired password are not implemented.

MySQL 5.7 also allows session SET statements while a password is expired. If ALTER USER names both existing and missing accounts, changes to the existing accounts remain effective before error 1396 is returned; changing the current account's credentials releases that connection's restriction. Modern releases retain the original accounts on this failure.

**Privileges are not enforced.** Grants do not limit the statements a session may run, and any password is accepted at connection. Password-expiry restrictions described above still apply.

## Transactions

- `START TRANSACTION` (with `READ ONLY`, `READ WRITE` and `WITH CONSISTENT SNAPSHOT`, which warns with 138 and is ignored below `REPEATABLE READ`), `BEGIN`, `COMMIT` and `ROLLBACK` (with `AND CHAIN` and `RELEASE`, and the default `completion_type` gives them), `autocommit`, `SAVEPOINT`, `ROLLBACK TO SAVEPOINT`, `RELEASE SAVEPOINT`, and the implicit commits of the statements that cause them. With `autocommit` off, a transaction starts with the first statement, so savepoints and `ROLLBACK` work without `BEGIN`; turning `autocommit` on commits it. A transaction is reported active (`SERVER_STATUS_IN_TRANS`, `PDO::inTransaction()`) from `BEGIN`, or once it read an InnoDB table or wrote a table.
- `CREATE TABLE ... START TRANSACTION` keeps an InnoDB definition unpublished until `COMMIT`; `ROLLBACK` and disconnect discard it. The connection permits only `BINLOG`, `COMMIT` and `ROLLBACK` while this transaction is active, including when `IF NOT EXISTS` kept an existing table. Temporary tables, non-atomic engines, foreign keys and `CREATE TABLE ... SELECT` are rejected.
- `SET [GLOBAL | SESSION] TRANSACTION ISOLATION LEVEL ... , READ ONLY | READ WRITE`, `transaction_isolation` and `transaction_read_only` (`tx_isolation` and `tx_read_only` in MySQL 5.6 and 5.7). Without a scope, and as `SET @@transaction_isolation`, the characteristics apply to the next transaction only, and setting them while a transaction is active fails with error 1568.
- Read-only transactions: a write of a table that is not temporary, `SELECT ... FOR UPDATE` of one, and creating or dropping a temporary table fail with error 1792; in a read-only session the statements that commit implicitly fail too.
- `XA START`, `END`, `PREPARE`, `COMMIT`, `ROLLBACK` and `RECOVER`, with the XA states and errors of the server.
- Statement atomicity: a statement that fails restores the rows it changed. `AUTO_INCREMENT` values it took are not given back, as in InnoDB.
- **RELEASE** ends the session once the statement is answered, as the server closes the connection: through `Server` the connection is closed and the statements after it in the same text do not run; a `Session` used in process is closed, and every later statement fails with error 2006 (`MySQL server has gone away`), as a client of a closed connection reports. The isolation level the server keeps for the next transaction when `SET SESSION TRANSACTION ISOLATION LEVEL` changes it inside a transaction, which decides warning 138, is not modeled.
- **Isolation between sessions**, as InnoDB isolates transactions. A consistent read sees a snapshot: under `REPEATABLE READ` (the default) the snapshot the first consistent read of the transaction took, or `START TRANSACTION WITH CONSISTENT SNAPSHOT`; under `READ COMMITTED` a snapshot for each statement; under `READ UNCOMMITTED` the latest rows, uncommitted changes included. Every level sees the changes of its own transaction. Locking reads (`FOR UPDATE`, `FOR SHARE`, `LOCK IN SHARE MODE`), `UPDATE` and `DELETE` read the latest committed rows; an `UPDATE` under `READ COMMITTED` or `READ UNCOMMITTED` reads a row another transaction holds semi-consistently, waiting for it only when its committed version meets the `WHERE` condition. Under `SERIALIZABLE`, a plain `SELECT` inside a transaction is a locking read (`FOR SHARE`); with `autocommit` on it is a consistent read.
- **Row locks.** A locking read locks the rows it returns, shared or exclusive, and `INSERT`, `UPDATE`, `DELETE` and the actions of foreign keys lock the rows they write exclusively, until the transaction ends. A statement that writes locks the rows it reads from other tables (`INSERT ... SELECT`, subqueries) shared under `REPEATABLE READ` and `SERIALIZABLE`. An insert that duplicates a unique key of a row another transaction holds waits for it, and a foreign key check locks the rows it reads shared, waiting for a referenced or referencing row another transaction holds. `NOWAIT` fails at once with error 3572, and `SKIP LOCKED` leaves the row out.
- **Lock waits.** Through `Server` or the `mysql-memory` command, a statement that needs a row lock another connection holds waits while the other connections are served, and once the lock is free reads the row again. The wait ends with error 1205 after `innodb_lock_wait_timeout` seconds, which rolls back the statement; a wait that would close a cycle is a deadlock, error 1213, which rolls back the whole transaction of the lighter transaction of the cycle (the one whose request closed it between equals). Sessions used in process (`Instance::connect()`) run one statement at a time, so nothing could release a lock while one waits: a conflicting lock fails at once with error 1205, and the timeout passes on the server's clock.
- **Storage engines that are not transactional.** A table of an engine other than InnoDB (`MyISAM`, `MEMORY`, `CSV`, ...) takes no row lock and no snapshot: every session reads its latest rows. Its changes stay when a statement fails or a transaction is rolled back, and the server's warning 1196 (`ER_WARNING_NOT_COMPLETE_ROLLBACK`) follows a failed statement, `ROLLBACK` or `ROLLBACK TO SAVEPOINT` that leaves such changes. From MySQL 9.0 on, a transaction that updates tables of InnoDB and of another engine warns once (6414).

Differences:

- **Locks are taken on whole rows that meet the conditions.** There are no gap or next-key locks, so an insert into a range another transaction read with a locking read does not wait. A statement locks, and waits for, only the rows that meet its `WHERE` condition, in their latest or committed version; the server locks every row it reads through the index it uses, which is every row of the table when no index serves the condition, so a statement that waits on the server can run at once here. The weight that chooses a deadlock's victim counts the rows each transaction changed and one group of locks for each table and lock mode, close to InnoDB's count of its lock structures.
- **A locking clause does not lock the tables of a view** the block reads, which the server merges into the block and locks.
- **Table locks, user-level locks and metadata locks never wait.** `LOCK TABLES` and `GET_LOCK()` do not block another session, and a statement that changes a table definition does not wait for the transactions that use the table.
- **XA PREPARE** releases the row locks of the branch, which the server keeps until `XA COMMIT` or `XA ROLLBACK`.

## Variables

- An expression assignment (`@v := expression`) has its own result type. Integer columns yield BIGINT, FLOAT yields DOUBLE, temporal values report connection-character-set string metadata, and JSON yields UTF-8 text with `utf8mb4_bin`. A later variable read has the wider variable type. Hexadecimal and bit literals assigned as strings lose their special numeric-literal interpretation; BIT columns store their unsigned integer value. These result and read types are checked against MySQL 8.0, 8.4 and 9.1.
- MySQL 5.6 and 5.7 assignments retain operand floating widths, unsigned decimal widths and fractional precision, with implicit coercibility even for numbers. String columns remain variable-scale strings, while assigned binary literals and temporal values retain their reported scale in arithmetic. Legacy string variables use MEDIUM_BLOB's byte bound for every character set. Decimal reads report width 83 in those releases and 67 from MySQL 8.0; their arithmetic precision remains 65 digits. Text conversion and reassignment retain the legacy decimal width, while materialization uses the stored precision and full scale. Legacy DIV keeps the dividend width up to 21 characters; modern floating DIV uses the full result width.
- User-variable reads retain whether the entry existed when that occurrence was resolved. In MySQL 5.6 and 5.7 an absent entry reads as NULL throughout that statement, even if a later expression assigns it. Explicitly assigning NULL with SET creates an entry and keeps subsequent reads live. From MySQL 8.0, CASE, IF, IFNULL and COALESCE infer absent variable operand types from the first other resolved result branch, including an explicit NULL; later branches then participate in the final result type. Legacy COALESCE retains a nullable result attribute whenever any argument is nullable.
- Every system variable of the selected release exists, with its scope (global, session or both), its default and its checks: a read-only variable, a global-only variable set for the session, or a value out of range is refused or adjusted as the server does. `SET` assigns all its variables or none.
- A session starts with the global values of the variables that have both scopes, so `SET GLOBAL` affects later sessions only.
- `statement_id` follows the server's sequence across client statements, including failures and SQL prepared executions. Wire preparation and statement closure also allocate numbers. `pseudo_thread_id` initially identifies the connection; assigning it changes `CONNECTION_ID()` without changing the transport connection. `identity`, `last_insert_id` and `LAST_INSERT_ID()` share the session's insert ID.
- Named key caches: `SET GLOBAL kc.key_buffer_size = ...` (or any other key cache parameter) creates the cache `kc`, and `@@GLOBAL.kc.key_buffer_size` reads its parameters; a cache that does not exist reads 0. MySQL 8.0 and later warn that this syntax is deprecated. No index is ever assigned to a cache. In MySQL 5.6 and 5.7 the catalog of system variables has no bounds for integer variables, so a value below the minimum of an unsigned variable is taken where the server raises it to the minimum.
- `SET PERSIST` and `SET PERSIST_ONLY` set the variable for the running server; nothing is written to an option file, and `RESET PERSIST` finds no persisted setting.
- `sql_mode` changes parsing (`ANSI_QUOTES`, `PIPES_AS_CONCAT`, `HIGH_NOT_PRECEDENCE`, `NO_BACKSLASH_ESCAPES`, `IGNORE_SPACE`), storage (the strict modes, `NO_ZERO_DATE`, `NO_ZERO_IN_DATE`, `ERROR_FOR_DIVISION_BY_ZERO`), grouping (`ONLY_FULL_GROUP_BY`) and the other behaviors the server ties to it.

Differences:

- **Direct character-set assignments** do not yet synchronize `character_set_connection` with `collation_connection`. Temporal assignment results with UCS-2, UTF-16 or UTF-32 connection collations still need separate handling of their reported collation and runtime bytes.
- **Values given at start** (`globals`, `--global`) are stored as written, without the checks and normalization of `SET GLOBAL`. `--global=sql_mode=ANSI` makes `@@sql_mode` read `ANSI`, where `SET GLOBAL sql_mode = 'ANSI'` stores the modes `ANSI` stands for.
- **Time zone.** The system time zone (`SYSTEM`) is UTC. `time_zone` takes an offset (`+05:30`) or a name of the time zone tables (`Europe/Paris`, `posix/...`, `right/...`), as a server whose tables are loaded does; an unknown name fails with error 1298. The clocks, `UNIX_TIMESTAMP`, `FROM_UNIXTIME` and `CONVERT_TZ` read it, and `TIMESTAMP` columns are stored in UTC and shown in it, so a value shows another time when `time_zone` changes. A local time that a change to summer time skips is stored as the instant of the change, with warning 1299 (error 1292 under a strict mode); a repeated local time is the earlier instant. Names and their ids come from the release catalogs in `resources/time-zones`, generated from live server tables by `bin/time-zones.php`. Conversion rules follow the tz database of PHP and keep after 2037 the offset in force at the end of 2037; so a zone whose rules changed since that database was published can differ. Leap seconds are not counted, as the server does not count them when its leap second table is empty.
- **Status variables** list the names and scopes of the release. `Questions` counts client statements, including parsing failures; `Queries` also counts stored-program work. Statement counters cover queries, writes, table and database DDL, stored programs, account and role privileges, transactions and XA, HANDLER, table locks, key caches, foreign servers, SET, FLUSH, RESET, diagnostic statements, catalog listings and prepared requests. Replication listing counters retain both old and new names where the release lists both. `FLUSH STATUS` resets all active sessions in MySQL 5.7 and later, and only the requesting session in 5.6; connection reset clears its own counters. Global command and traffic contributions remain until server restart. `Aborted_clients` counts authenticated wire connections closed without COM_QUIT, including KILL and transaction RELEASE; it is global in both SHOW scopes and `FLUSH STATUS` resets it. `Flush_commands` counts full table-cache flushes and resets of enabled binary logs, once per statement, and survives `FLUSH STATUS`. Flushing named tables or other resources changes `Com_flush` without increasing this total. The legacy wire COM_REFRESH command applies its table-cache, log, replication and status flags, commits an open transaction and counts one Com_flush. MySQL 5.7 and 8.0 append its deprecation to existing conditions in SHOW WARNINGS and report the total in the OK packet; the mysqlnd refresh API retains its earlier warning and insert-ID fields. Legacy refresh flags also enforce binary-log and server-ID requirements, with both failure conditions retained when both resets fail in MySQL 5.6. MySQL 8.3 and later reject this removed command with error 1047 without committing. A supervised restart begins new counters; closing old connections or sending their final replies cannot contribute to the new server totals. `Uptime` and `Uptime_since_flush_status` include simulated waits and use the reading statement's timestamp, including unsigned wraparound when `SET timestamp` predates the real start or flush time. `Threads_connected` counts current clients and `Connections` counts clients opened since startup. `Max_used_connections` retains the peak after disconnects; `FLUSH STATUS` resets it to the current count. Its timestamp uses the real server clock and is displayed in the reading session time zone, independently of `SET timestamp`. The enabled event scheduler contributes to `Threads_running`, but waiting client statements are not yet included. `Bytes_received` and `Bytes_sent` count uncompressed protocol packets, including headers, per connection and globally. Client statements in a batch send each response before executing the next statement; in-process sessions generate no network traffic. Procedure result sets are sent as each statement produces them, including nested and prepared CALLs; the next statement observes their traffic before the final completion or error. `PDO::ATTR_SERVER_INFO` and `mysqli::stat()` read the same global values through COM_STATISTICS. Its `Questions` field reports global `Queries`, including the statistics request; the request does not increment `Questions`. The average truncates to three decimals and uses the pinned timestamp, including zero uptime and unsigned wraparound. Diagnostics and ROW_COUNT remain intact. Other command counters, physical storage and operating-system counters remain incomplete and retain catalog defaults; unrestricted `SHOW STATUS` does not yet match a real server.

`max_error_count` limits stored conditions, including errors, without reducing `@@warning_count`, `@@error_count` or the warning totals in replies. Protocol warning fields saturate at 65,535. `GET DIAGNOSTICS NUMBER` counts the stored conditions; an error handler can still `RESIGNAL` its original error when the storage limit is zero. A procedure returns its stored conditions to the caller, so counts of unstored conditions do not survive that boundary. A `RESIGNAL` with a new SQLSTATE reserves a slot by discarding the oldest stored conditions when necessary. For `RESIGNAL` without SQLSTATE, MySQL 5.6 retains only the last stored condition when the previous area had a spare slot; a full area becomes empty, while the error still reaches the caller.

In MySQL 5.6 the diagnostics area is cleared only by a statement that opens a table; `SHOW WARNINGS` after a statement that opens none, such as `SELECT @@sql_mode`, `USE`, `CREATE DATABASE`, `GRANT ... ON *.*` or `SET`, still lists the conditions of the statement before it, as the server does.

In MySQL 5.6 and 5.7, sorting expressions outside the visible select list can run before the next row updates its stored output fields. Seeded random calls advance for these key reads before their visible reads; nested aliases of direct assignments copy the last stored field back to the variable, initially the field's zero value. An assignment inside a larger expression can execute again for each key read. The access path records this evaluation order independently of the result's column order.

For ordinary DISTINCT queries, varying string fields use stored metadata while constant expressions retain their original metadata. Full results, sorting and SQL_CALC_FOUND_ROWS finish input effects before copied assignment fields are read for output. A sorting alias also reads its stored assignment before LIMIT, including when OFFSET discards every row. Constant assignments are deferred until a row is returned; counting discarded DISTINCT rows does not execute those assignments. MySQL 5.6 and 5.7 can stop after probing one input row when an unsorted bounded query has no table-dependent output expressions; sorting and SQL_CALC_FOUND_ROWS retain the remaining input. Legacy copied fields retain their expression origin.

On MySQL 8.0 and later, ROLLUP evaluates aggregate arguments in grouping order, visiting the grand total, subtotals and leaf group for each aggregate before advancing to the next aggregate. GROUP_CONCAT and COUNT(DISTINCT) share their captured arguments across levels. With varying grouping keys and window functions, aggregate inputs are stored once in source-row order; constant grouping keys retain per-level reads. Predicates stored this way become numeric fields for JSON aggregation. GROUP_CONCAT resolves equal sorting keys in reverse input order and preserves that ordering on repeated result reads.

A ROLLUP query whose entire ORDER BY list matches a leading prefix of its GROUP BY keys folds groups in those directions; remaining grouping keys ascend. Aliases and output positions resolve to their grouped expressions. Computed keys, subtotal keys or extra ordering items retain the ordinary grouping input order and sort only the output. This also controls concatenation and assignment effects before windows and DISTINCT.

MySQL 5.6 and 5.7 evaluate every aggregate for a ROLLUP leaf before advancing through subtotal levels to the grand total. COUNT(DISTINCT) and GROUP_CONCAT capture their arguments at the leaf and share those values across levels. MySQL 5.7 JSON_OBJECTAGG keeps the first value for a duplicate key; modern releases keep the last.

Implicit aggregation and constant GROUP BY keys retain direct result metadata, even with DISTINCT or window functions. Constant ROLLUP keys still introduce output rows; DISTINCT compares aggregate parents and republishes copied assignments there. Varying ROLLUP keys defer aggregate parents beyond a window DISTINCT stage. Ordinary aggregate assignments beside a window execute from the current aggregate row, including each ROLLUP total.

With varying grouping keys and a window stage, parents of `GROUP_CONCAT`, `JSON_ARRAYAGG`, and `JSON_OBJECTAGG` retain expression metadata and are evaluated after DISTINCT removes duplicates using the remaining stored outputs. Bare aggregate fields still participate in duplicate removal. Scalar parents of `MIN` and `SUM` remain duplicate keys without ROLLUP, including wide string expressions.

Computed aggregate parents in MySQL 5.6 and 5.7 also retain their expression metadata when implicit aggregation or constant GROUP BY produces one group. DISTINCT does not materialize those parent expressions; varying ROLLUP groups retain their separate storage behavior.

On modern releases, COUNT(DISTINCT) and GROUP_CONCAT distinguish constant NULL checks, complete grouped input tuples and stored window inputs. Explicit groups evaluate all tuple arguments before rejecting a row containing NULL; GROUP_CONCAT reads sorting keys first. Implicit COUNT(DISTINCT) omits table-independent fields from its row keys. Implicit GROUP_CONCAT evaluates deferred constant expressions after sorting accepted tuples. Streaming GROUP_CONCAT retains its expression metadata until a DISTINCT or window stage stores the result. These phases are checked through returned values, field metadata and user-variable effects.

Without an explicit ordering clause, MySQL 5.7 and later visit GROUP_CONCAT(DISTINCT) tuple keys in sorted order before reading deferred expressions. On modern releases, constant ORDER BY keys retain their tie ordering even when their expressions need not execute; variable assignments in such implicit constant keys do not run.

On MySQL 8.0 and later, COUNT(DISTINCT) checks constant arguments before scanning, including over empty tables and in correlated subqueries whose checks precede the outer projection. Statically false WHERE or HAVING clauses, absent constant primary-key rows and LIMIT 0 without an offset suppress these checks. MySQL 5.7 prepares nested checks before applying outer bounds; MySQL 5.6 waits until the nested block first executes. Resolved constant assignments are checked once and omitted from tuple keys. Legacy assignments that read session or row values still run for every tuple, including tuples rejected for NULL. Explicitly grouped tuple aggregates run in group order. GROUP_CONCAT keeps direct expression metadata across these releases; MySQL 5.6 preserves DISTINCT tuple arrival order when no ORDER BY is specified, while later releases sort the distinct values.

Direct MySQL 5.6 and 5.7 ROLLUP columns retain their base-column NOT NULL and key flags, even though a total row can contain NULL. MySQL 5.6 removes the base origin for constant primary-key lookups. MySQL 5.7 removes it when the key exists and preserves it when the lookup finds no row. Semantic NULL facts remain separate from these protocol flags.

With ONLY_FULL_GROUP_BY, MySQL 5.7 and later reject DISTINCT ordering expressions that reference an unselected column or contain an unselected owned aggregate. The first offending reference determines the error. Selected aliases, independent subquery aggregates and group keys that make DISTINCT redundant are resolved separately. MySQL 5.6 permits unselected DISTINCT ordering expressions, but still rejects unaggregated ordering columns in an aggregate query without GROUP BY (error 1140).

On MySQL 5.6 and 5.7, DISTINCT over varying, unrolled groups stores scalar string fields with stored metadata. Computed numeric keys can compare NULL equal to zero while retaining the first returned value. Hashed groups preserve arrival order before duplicate removal when DISTINCT introduces new keys or an explicit output order replaces implicit group sorting. Redundant DISTINCT without an output order retains implicit sorting; streaming tuple aggregates, ROLLUP and indexed grouping retain their input ordering.

MySQL 9.1 emits a grand-total row for an executed empty ROLLUP input, with NULL grouping keys, zero COUNT and each other aggregate's empty-input value. Earlier releases emit no rows. Statically false predicates and absent constant primary-key lookups suppress the total.


Legacy UNION bounds preserve operand evaluation separately from returned rows. MySQL 5.6 also bounds the last operand of an unordered UNION while retaining earlier operands; SQL_CALC_FOUND_ROWS counts that operand's remaining input without projecting it. MySQL 5.7 streams an unordered UNION ALL without DISTINCT boundaries, skipping the visible expressions of discarded rows. If its last operand is a constant SELECT, FOUND_ROWS reports returned rows. A final table operand reports consumed rows including OFFSET until the bound is reached; an exhausted stream or SQL_CALC_FOUND_ROWS reports table input alone. Materialized legacy unions retain their buffered row count under a global LIMIT. Combined legacy integer columns preserve wider expression bounds above the BIGINT storage width; replacing a leading NULL field allocates the 20-character integer storage width, while a trailing NULL preserves the first integer expression's width.

## Inspection

- `SHOW TABLES`, `SHOW COLUMNS` and `DESCRIBE`, `SHOW INDEX`, `SHOW DATABASES`, `SHOW [FULL] PROCESSLIST`, `SHOW STATUS`, `SHOW TABLE STATUS`, `SHOW OPEN TABLES`, `SHOW CREATE DATABASE`, `TABLE` and `VIEW`, `SHOW VARIABLES`, `SHOW COLLATION`, `SHOW CHARACTER SET`, `SHOW ENGINES`, `SHOW ENGINE`, `SHOW PLUGINS`, `SHOW PRIVILEGES`, `SHOW PROFILES`, `SHOW WARNINGS`, `SHOW ERRORS`, `SHOW COUNT(*) WARNINGS`, and the `SHOW` statements of stored programs, accounts and replication, with the column metadata of the server.
- `SHOW TABLE STATUS` reports the figures InnoDB reports for a table of one page.
- Table creation times retain the DDL statement clock in MySQL 8.0 and later; MySQL 5.6 and 5.7 use the actual clock. Update times track committed writes, including XA commits and nontransactional MyISAM writes, independently of `SET timestamp`. These actual-clock readings include the elapsed sleeps and waits that `SYSDATE()` sees. InnoDB update times are unavailable in MySQL 5.6 and are cleared by table rebuilds, truncation and restart on modern releases; MySQL 5.7 retains the previous update time after TRUNCATE and records a new actual-clock time when ALTER copies nonempty rows. Readers see times in their session time zone. Table statistics expire according to `information_schema_stats_expiry` and the session clock; setting the expiry to zero bypasses the cached values without replacing them. A cached table-statistics observation survives ALTER and TRUNCATE until it expires.
- `HELP` finds no topic: the server's help tables are not included.
- `SHOW OPEN TABLES` reads the table-handle cache, separately from the catalog. Table reads, writes, SHOW CREATE TABLE and ALTER open base-table handles; temporary tables stay outside the shared cache. HANDLER cursors and LOCK TABLES contribute to `In_use`, including uses held by another session. FLUSH, DROP and RENAME invalidate the affected handles.
- `EXPLAIN` generally answers one row per table with access type `ALL` in the traditional format, and scan documents for `TREE` and `JSON`. An unrestricted single-table InnoDB UPDATE with an integer primary key reports the clustered index scan and marks a primary-key change as `Using temporary`. MySQL 5.6 uses its ten-column layout, with the columns added by EXTENDED or PARTITIONS, and describes unrestricted DELETE as `Deleting all rows`. This is not a complete optimizer or cost model; other table access plans can differ from the server.

Differences:

- **`SHOW PROCESSLIST`** lists client sessions and the event scheduler daemon while `event_scheduler` is `ON`. Client hosts include their TCP source port. Connection identities remain stable across `COM_RESET_CONNECTION` and share an allocator with daemon identities and wire greetings, including abandoned handshakes. Session elapsed time follows the statement clock, including a pinned `timestamp`; daemon elapsed time follows the server clock. Creating or enabling a future event wakes the daemon into its next-activation wait. Event bodies and scheduled wakeups are not executed.
- **The table cache does not model every internal access.** Internal dictionary handles opened by server startup and metadata-changing statements, capacity-driven eviction, pending lock requests and transient name locks are not fully represented. The differential fixture disables background statistics recalculation, analyzes the fixture tables synchronously and flushes both caches before each input; populated-cache regressions separately check the modeled transitions.
- **`CHECKSUM TABLE`** answers a stable checksum of the rows, which is not the server's.

## System tables

The databases `information_schema`, `mysql` and `performance_schema` hold every table a server of the emulated release has, with its columns and the column metadata a result reports: names, types, lengths, collations, flags, and the base table and database each column is read from. Their names are found as on the server: the name of `INFORMATION_SCHEMA` and of its tables in any case, the others as written. In MySQL 8.0 and later a column of an `INFORMATION_SCHEMA` view is named as the view names it, in any case the statement writes it. The rows are computed from the state of the server each time a statement reads a table, so the tables can be joined, filtered, sorted, grouped and read in subqueries and views like any other. `SHOW TABLES`, `SHOW COLUMNS` and `DESCRIBE` list them.

| Tables | Rows |
|---|---|
| `SCHEMATA`, `TABLES`, `COLUMNS`, `STATISTICS`, `KEY_COLUMN_USAGE`, `TABLE_CONSTRAINTS`, `REFERENTIAL_CONSTRAINTS`, `CHECK_CONSTRAINTS`, `VIEWS` | The databases, tables, views, columns, keys and constraints of the dictionary, and the system tables themselves in `TABLES` and `COLUMNS` |
| `ROUTINES`, `PARAMETERS`, `TRIGGERS`, `EVENTS` | The stored programs |
| `CHARACTER_SETS`, `COLLATIONS`, `COLLATION_CHARACTER_SET_APPLICABILITY`, `ENGINES`, `PLUGINS`, `KEYWORDS`, `RESOURCE_GROUPS`, `ST_SPATIAL_REFERENCE_SYSTEMS` | Those of a server of the release |
| `USER_PRIVILEGES`, `SCHEMA_PRIVILEGES`, `TABLE_PRIVILEGES`, `COLUMN_PRIVILEGES`; `mysql.user`, `db`, `tables_priv`, `columns_priv`, `procs_priv`, `global_grants`, `proxies_priv`, `role_edges`, `default_roles`, `servers` | The accounts, roles, grants and foreign servers |
| `PROCESSLIST`, `performance_schema.processlist` | The sessions connected |
| `performance_schema.global_variables`, `session_variables`, `variables_by_thread`, `global_status`, `session_status`, `status_by_thread`; in 5.6, `INFORMATION_SCHEMA.GLOBAL_VARIABLES` and the like | The system and status variables |
| `mysql.time_zone`, `mysql.time_zone_name` | The named time zones, numbered as `mysql_tzinfo_to_sql` numbers them |

Differences:

- **The other tables are empty.** The InnoDB tables of `INFORMATION_SCHEMA`, `FILES`, `PARTITIONS`, `OPTIMIZER_TRACE`, the role tables (`APPLICABLE_ROLES` and the like), the instrument, event, lock and thread tables of the Performance Schema, the help tables and the time zone transition tables of `mysql`, and the other system tables hold no row. The `sys` database holds no table.
- **Figures and times are the emulator's.** The figures of `TABLES` are those of `SHOW TABLE STATUS`; a system table reports 0 rows and bytes. Creation times of system tables, the times of grants and of password changes are the time the server started, and grants are recorded as made by `root@localhost`. Password hashes differ from the server's, as their salts do.
- **Privileges do not filter rows.** Every account sees every row, as root does.
- **Order without `ORDER BY`.** The rows come in the order the server returns them for a plain scan of the table; a server that reads a table through an index can return them in another order.
- **`ST_SPATIAL_REFERENCE_SYSTEMS`** has empty definitions: the emulator does not carry them.
- **`INFORMATION_SCHEMA.PARAMETERS.PARAMETER_MODE`** is sent as a `CHAR` column; the server sends the `ENUM` type code.
- **Writing a system table** is refused: a table of `INFORMATION_SCHEMA` with error 1044, a table of the Performance Schema with error 1142, as the server refuses them; writing or altering a table of `mysql` fails with error 1235. `SELECT ... FOR UPDATE` of an `INFORMATION_SCHEMA` table is not refused.

## Performance

The emulator is meant for the small tables of tests. It has no optimizer and does not use indexes to find rows: every table is scanned, every join reads its inner table once for each row of the outer one, and every sort, grouping and `DISTINCT` reads its whole input. A query over two tables of n rows each costs on the order of n² row reads.
