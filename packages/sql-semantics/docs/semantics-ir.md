# Complete SemanticsIR values

`SqlSemantics\SemanticsIR` and `SqlSemantics\Analyzer` are shared interfaces. The database package supplies the operation classes, operand types, scope checks, and SQL representation. All three database packages provide checked projections. Each package supports joined base-table occurrences in its checked projection domain. Each implementation fixes its own language profile and operand roles.

```php
use SqlSemantics\Platform\Sqlite\Semantics;

$sqlite = new Semantics();
$catalog = $sqlite->context(['CREATE TABLE accounts (Id INTEGER, balance INTEGER)']);
$ir = $sqlite->analyze(
    'SELECT id, accounts.id, balance - ?2 AS remaining FROM accounts',
    $catalog,
);

assert($ir->columns[0]->expression->slot === $ir->columns[1]->expression->slot);
echo $ir->toString();
```

The source has an absolute schema and table name. Its ordered slots carry only the names of the referenced columns. Both occurrences of `id` refer to one slot. The output name `Id` is a separate value, and the two occurrences remain separate positions in the result. Interpreting or rendering the value requires no parser or declaration context. Evaluation supplies the same external objects and SQLite storage values and binds the numbered parameter at slot 2.

You can build the same structure directly with classes in `SqlSemantics\Platform\Sqlite\Ir`. Use `TableSource` to declare the external column slots, `ColumnReference` to address a slot, `ResultColumn` to associate an expression with its output name, and `Select` to close the scope. A direct source is an assertion about the external schema supplied for evaluation. Analysis establishes that assertion against the supplied declaration.

## Supported SQLite scope

- One SELECT with explicit result expressions and up to 64 base-table occurrences. A source must resolve to a complete declaration. Each column resolves to an explicit member of a specific occurrence. Two aliases of the same table have different occurrence indices.
- INNER, CROSS, LEFT, RIGHT and FULL joins with optional ON, and filtering with WHERE. The supported predicates include scalar truth conversion, comparisons and AND or OR. Each ON clause sees its join prefix. The filter sees the completed joined input.
- An ordinary binary INNER, CROSS or LEFT join can use USING or NATURAL. The IR contains a normal join with comparisons in left-to-right operand order and resolves the wildcard and merged output to exact slots. Qualified names retain their respective inputs. RIGHT selects the right slot for a merged result. A wildcard keeps the left heading and spelling for that position. A qualified left wildcard still reads the merged representative, while an explicit left column use reads its own slot. FULL uses an ordered COALESCE of the two resolved fields. It uses the original expression spelling for an unaliased merged result name.
- A multi-step chain of ordinary INNER, CROSS and LEFT joins can use USING and NATURAL. A key compares the first matching name in the earlier inputs with a field of the new right input. Each comparison retains both occurrence indices and its own scope.
- ORDER BY on one-based output positions, including ASC, DESC and either NULL placement. Rows with equal keys can appear in any relative order.
- SELECT ALL and SELECT DISTINCT. DISTINCT uses the collation of each output expression and preserves an eligible typed representative of each equivalent row.
- LIMIT and OFFSET with signed decimal integers or numbered parameters. The limit records count and offset separately. The comma form keeps the lexical order of parameter labels. With a bound cutting into an ordering tie, the engine can choose any eligible rows in that tie.
- Signed 64-bit integer literals and hexadecimal integers, decimal REAL literals, UTF-8 TEXT, BLOB, NULL, numbered SQLite parameters, and resolved column slots. REAL operands retain their decimal components so the selected SQLite engine determines rounding and signed zero. TEXT keeps decoded characters and BLOB identifies bytes by hexadecimal pairs.
- Binary addition, subtraction, multiplication, comparisons, AND, and OR compose as scalar expressions in projections, filters, join predicates, VALUES rows, and assignments.
- Numeric scalar expressions preserve division, remainder, bitwise AND and OR, and signed shifts with their explicit operand order. SQLite supplies its native numeric coercion, storage class and NULL behavior.
- SQLite `||` holds the left and right scalars in order. It preserves NULL and appends the exact TEXT bytes of the native conversions, including BLOB bytes and embedded NUL.
- SQLite LIKE and GLOB retain the subject, pattern and negation. LIKE also retains its optional ESCAPE operand. The fixed built-ins use ASCII case folding for LIKE and case-sensitive character matching for GLOB.
- A direct SQLite TEXT constant can hold a zero code point. Its SQL representation preserves the full TEXT bytes and the absence of literal affinity.
- The SQLite `Collation` enum identifies `BINARY`, `NOCASE` and `RTRIM` for scalar `COLLATE`, grouping and distinct counts. A collated scalar keeps its own value and affinity.
- Scalar `IN` and `NOT IN` retain the tested value and the ordered list, including duplicate members and an empty list. The renderer preserves numbered binding registration in the empty form. Analysis records the decided integer outcome and surviving numbered bindings when SQLite folds away an unused operand.
- SQLite range tests retain one tested scalar, its inclusive lower and upper bounds, and negation. The two comparisons use their respective affinities and collations.
- Prefix expressions retain unary plus, logical NOT and bit complement. Analysis distinguishes signed numeric literals from computed negation. Postfix NULL tests use the explicit NULL-safe comparison role.
- Bare truth words resolve as visible columns or INTEGER constants. An unshadowed right-hand truth word in IS or IS NOT selects a Boolean test. The emitted test preserves that binding when a table has a field named true or false.
- Scalar CASE retains its optional base, ordered decisions and results, and optional fallback. The engine evaluates conditions and results lazily. Simple CASE uses the affinity and collation of its operands. Numbered parameters retain their lexical registration even in skipped branches.
- COALESCE and binary IFNULL keep their ordered scalar arguments. Evaluation returns the first non-NULL value with its native storage class. The structure also retains parameters in arguments skipped during evaluation.
- CAST holds its effective INTEGER, REAL, NUMERIC, TEXT or BLOB conversion and one checked scalar operand. Analysis resolves the affinity before publication. Rendering uses the canonical type name and preserves the observed result label.
- Result order, result names, SQLite storage classes and values, repeated rows, and numeric parameter slots and labels. Without an ordering clause, the result is a multiset. The ordering contract fixes the relative order of rows with different keys.
- The default UTF-8 profile with short column names enabled and full column names disabled. The engine uses the standard SQLite 3.47.2 limits. The initial IR domain also bounds identifier length, the number of result columns, and expanded expression size.
- Top-level DELETE of one declared base table. The IR records the absolute target and checks any WHERE predicate against its slots. Unqualified RETURNING fields and star expansion read the deleted row with resolved column names and order. Expression and qualified RETURNING inputs, WITH and explicit index choices remain open. The DELETE changes rows when the caller executes its output. Execution supplies the same target definitions and trigger rules.
- Top-level VALUES with fixed-width, nonempty rows of scalar expressions evaluated without table inputs. Its result names are column1 through columnN, and each written row contributes one result row.
- Compound queries combine SELECT and VALUES arms through UNION ALL, UNION, INTERSECT and EXCEPT. Arms have equal width and keep their individual scopes. The compound exposes the first arm’s result labels and supports ordinal ORDER BY and LIMIT when the last arm is SELECT.
- A projection from one ordinary CTE whose definition is VALUES with explicit column names. The IR carries the definition and its ordered column slots in a `LocalSource`. The same definition can occur on either side of a join or in several occurrences. Each reference selects its occurrence and column independently. The CTE supplies the rows even when the database contains a same-named base table. Multiple definitions, materialization hints and recursive CTE joins remain open.
- Grouped SQLite queries retain each column slot and its effective BINARY, NOCASE or RTRIM collation. COUNT can count input rows, nonnull field values or distinct values under a resolved collation. A grouped key retains the selected representative’s value and storage class. The optional WHERE filters input rows with a scoped scalar. The optional HAVING compares a count with an integer, NULL or a numbered parameter in either operand order. Custom collations, other aggregate functions and general aggregate expressions in HAVING remain open.
- One recursive CTE with named slots, an independent VALUES or scalar SELECT anchor, and a single self-fed SELECT arm. The definition holds the ordered successor expressions, the optional filter, and the UNION duplicate policy. The consumer reads the same scoped slots. Recursive joins, multiple arms, recursive queue limits and queue ordering remain open.
- Top-level INSERT associates written values with an ordered list of writable target slots. Its absolute table and optional RETURNING fields share one local layout. The RETURNING fields read the inserted row before changes from AFTER triggers, including fields supplied by defaults and generated fields. The statement may inherit the table policy or specify ABORT, IGNORE, FAIL, ROLLBACK or REPLACE. The standalone REPLACE verb has the same role as INSERT OR REPLACE. The targetless DO NOTHING action skips uniqueness violations independently of that statement policy. WITH, explicit conflict targets, DO UPDATE and general RETURNING expressions remain open.
- A SQLite generated column records its storage mode and a scalar expression over declaration slots. A complete table verifies that the references exist and form an acyclic dependency graph. It requires an ordinary column and keeps generated columns outside defaults and primary keys. When a declaration omits the generation mode, analysis records VIRTUAL.
- A SQLite DEFAULT VALUES input inserts one row using the same target declaration. When a VALUES or SELECT write omits the column list, analysis resolves all writable columns in declaration order and preserves their correspondence to the input. Generated columns remain under the target declaration.
- An SQLite INSERT can take a checked SELECT input. Its projection order matches the declared writable slots. The target policy, typed rows, source filters, DISTINCT, ordering, bounds and parameter markers remain part of the complete value.
- Top-level UPDATE with scalar assignments and optional WHERE on one resolved base table. Assigned expressions read the old row and use the same local slots as the assignment targets. Written order preserves repeated assignments and numbered parameter registration. The optional RETURNING projects the named slots of the new row before changes by AFTER triggers. Its fields can read generated values. The statement records inheritance or the exact ABORT, IGNORE, FAIL, ROLLBACK or REPLACE policy. WITH, FROM, row assignments, index choices and general RETURNING expressions remain open.
- DROP TABLE for a resolved ordinary table or a known schema-qualified absence under IF EXISTS. The absolute name preserves the target, including when a temporary table shadows a main table. SQLite applies the matching schema's foreign key rules during execution.
- A resolved SQLite source records its absolute name, table or view kind, and the consumed column slots. Read positions can reference a checked view. The INSERT, UPDATE, and DELETE targets for the admitted write forms require a base table.
- CREATE VIEW records an absolute destination, an ordered list of effective names and a checked SELECT projection, grouped COUNT query, VALUES, or a compound without declared-type affinity in its projected slots. A persistent view resolves unqualified sources in the destination schema. A temporary view uses the regular search path. Projection bodies can contain one checked local VALUES or recursive definition. Every view body rejects parameter registrations, including registrations in a local definition.
- DROP VIEW for an absolute resolved view or a guarded, schema-qualified absence. View removal applies SQLite's owned-trigger and catalog rules. The underlying rows and neighboring schema objects retain their identities and values.
- CREATE TABLE for ordinary and STRICT tables with ordered columns, an optional NOT NULL conflict policy and the declared INT, INTEGER, TEXT, REAL, BLOB or ANY type. The IR resolves the creation schema, preserves IF NOT EXISTS, and permits untyped columns in ordinary tables. STRICT requires an explicit type and preserves the native no-coercion behavior of ANY. Checked literal defaults retain their storage role and distinguish explicit SQL NULL from an omitted clause. A NOT NULL constraint retains its effective conflict algorithm, including REPLACE with a default. A primary key keeps its resolved slots, collation, order, placement and conflict algorithm. WITHOUT ROWID requires a primary key. AUTOINCREMENT requires an INTEGER rowid alias and preserves the native persistent allocation mode. Computed defaults, additional types and additional constraints remain open.
- CREATE TABLE AS declares and populates a resolved table from standalone VALUES or a source-free SELECT. The created columns expose deterministic names and declaration types. The checked query supplies every ordered operand and numbered parameter.
- SQLite column-based tables own the ordered sequence of primary and unique keys. Inline keys refer to their owning column slot and inherit its builtin collation. Table key terms retain their resolved collations and sort directions. The declaration distinguishes omitted and explicit conflict policies, and rejects conflicting policies for equivalent native indexes.
- An explicitly named SQLite CHECK constraint keeps its decoded failure label, its position on the table or an owning column, and a checked expression over declaration slots. The table owns the conditions in evaluation order. SQL emission uses the resolved column names, so a column qualification used during analysis does not change the stored binding. An empty membership inside a CHECK preserves the numbered markers SQLite registers and the decided condition value. Live markers and subqueries in the CHECK remain prohibited. The same declaration scope also supports unnamed comparisons between a declared column and a nonnegative decimal integer. Their checked name spelling, comparison token and diagnostic presentation preserve native failure labels and the effects of ALTER TABLE RENAME COLUMN. Other implicit label expressions and hidden rowid operands remain open.
- SQLite table and column renames specify the absolute table and the decoded destination. A column rename also binds the canonical declared member and records whether to quote every rewritten reference or to use the original reference's quoting. That choice can change how SQLite reparses dependent objects. The native catalog and active transaction govern dependency errors and rollback.
- SQLite index creation records the owning schema, bound ordered keys and optional partial predicate. A CAST used in an index may carry a checked native type name. Indexed binary IFNULL preserves its builtin identity. Both are observable when a query forces a specific index.
- SQLite index removal selects the index and owner in an absolute schema. An optional absence keeps its exact qualification scope so emitted SQL verifies the same native schemas.
- SQLite index rebuilding distinguishes all indexes, one builtin collation, one resolved relation, and one resolved index. A bound index includes its absolute schema and owner.
- SQLite statistics collection distinguishes the global persistent scope, a selected schema, an absolute relation, and an absolute index. Its schema and index priority follow native ANALYZE.
- BEGIN with its effective lock mode, COMMIT, ROLLBACK, SAVEPOINT, RELEASE and ROLLBACK TO. The value identifies the transition and carries the decoded checkpoint label when needed. The same connection is responsible for its transaction stack and lock state. RELEASE and ROLLBACK TO address the most recent matching checkpoint at execution.

`Semantics::analyze()` returns the complete value. Handle `SqlSemantics\AnalysisException` for malformed, unresolved or unsupported input. `analyzeAll()` applies the same contract to each statement against the same explicit context.

Use `Semantics::context()` to provide a catalog of relation definitions for name resolution. Each call to `analyzeAll()` binds against the same context. The result contains the complete statements in script order.

Wildcards expand into the same explicit result columns as individually written fields. A wildcard needs a closed declaration layout. The result retains each output name and its exact input occurrence. A qualifier on a self join selects the specific occurrence.

## MySQL and PostgreSQL statements

MySQL supports NATURAL and USING over two declared ordinary inputs with signed INT keys. The result preserves the native merged heading order and qualified slots. A RIGHT JOIN with an explicit ON keeps the original physical column order.

Call `analyze()` on the MySQL or PostgreSQL `Semantics` object configured for the target release. Their database-owned `Ir` namespaces provide direct construction with the same invariant checks.

- The projection supports zero or one ordinary base-table input or a binary join tree of external and independent derived inputs. It supports explicit result expressions, signed 32-bit integer literals and column slots, truth values, NULL, and signed addition, subtraction and multiplication. Truth values and literal NULL occupy result positions. Signed arithmetic takes integer expressions.
- CROSS, INNER, LEFT and RIGHT joins preserve operand grouping and scopes. PostgreSQL also supports FULL joins with signed integer equality between opposite inputs. ON sees the leaves of that specific join. WHERE sees the full source and keeps only true rows. Expressions refer to each occurrence by its ordinal and local column slot, including both sides of a self join.
- MySQL records the named database and uses the native default lexical settings, UTF-8 through `utf8mb4`, `lower_case_table_names=0`, and empty `sql_mode`. An unqualified table requires a declaration context with a named current database. MySQL reports signed INT table values, integer arithmetic, and the NULL result with their native result types.
- PostgreSQL binds integer slots to `int4` declarations, preserves `ONLY`, and emits `pg_catalog`-qualified integer operators. Unqualified input operators require `pg_catalog` ahead of user schemas in the relevant search path. An explicitly qualified builtin operator can supply its identity directly.
- MySQL projections support explicit signed and unsigned BIGINT casts of checked integers, signed arithmetic, Booleans and NULL. Nested conversions preserve each target, and CAST and CONVERT preserve the result name. For a UNION mixing these result kinds, MySQL 5.6 and 5.7 can clip values to the first arm’s signedness. MySQL 8.0 through 9.1 promote mixed signed and unsigned integer results to an exact decimal type.
- MySQL projections support plain `utf8mb4` literals. `Literal\TextLiteral` holds the decoded value, including embedded NUL and supplementary Unicode characters. The complete SELECT's `release->textCollation()` gives the required `collation_connection`. Use `utf8mb4_general_ci` on MySQL 5.6 and 5.7 and `utf8mb4_0900_ai_ci` on the supported 8.x and 9.x releases, with `sql_mode` empty. An adjacent literal contributes the first segment's native result label and the concatenated value. [Native text literal contract](../assurance/mysql-text-literal-v1.json)
- Top-level DELETE supports one resolved ordinary target and an optional Boolean, NULL or signed-integer comparison filter. PostgreSQL preserves ONLY and includes descendant tables when ONLY is absent. An ordered PostgreSQL RETURNING list reads named int4 and native text fields of each deleted row, including closed wildcard expansion. The database applies deletion and triggers when the SQL runs.
- MySQL signed arithmetic accepts `DIV`, `%` and infix `MOD`. Its quotient truncates toward zero, the remainder follows the dividend sign, and a zero divisor produces NULL in the empty SQL mode. The output uses the native ordered operators so evaluation retains the selected release’s signed integer bounds.
- PostgreSQL int4 arithmetic resolves division, remainder, bitwise AND, OR and exclusive OR in addition to addition, subtraction and multiplication. Qualified builtin operators retain signed results and NULL behavior. Division by zero and integer overflow retain their native SQLSTATE outcomes.
- A PostgreSQL searched CASE with a resolved int4 result retains up to 32 ordered Boolean decisions, their int4 or NULL results, and an optional fallback. Every branch uses the enclosing source scope. Only TRUE selects an arm. Explicit NULL results keep their int4 type in the emitted SQL.
- A MySQL signed range test carries one subject and two ordered inclusive bounds. Its typed integer operands support the signed 64-bit interval. The result is 1, 0 or NULL, with negation recorded independently.
- A MySQL signed membership test records the probe, ordered alternatives and `IN` or `NOT IN` polarity. Resolved fields point to a declared signed width and NULL policy in the owning occurrence. Duplicates remain present. A match decides the result before NULL propagation, and a filter accepts only native true. [MySQL signed membership contract](../assurance/mysql-signed-membership-v2.json)
- A MySQL signed CASE keeps the simple subject or searched truth decisions, the WHEN/THEN alternatives in order, and a distinct optional ELSE. The completed SELECT derives the native protocol width and nullability from those operands, the source occurrences and its release. [MySQL signed CASE contract](../assurance/mysql-signed-case-v1.json)
- A MySQL truth test returns a nonnull native integer and retains its exact comparison to true, false or unknown, including explicit negation. Its operand keeps the resolved signed field width or nested predicate. [MySQL truth contract](../assurance/mysql-native-truth-v1.json)
- A PostgreSQL int4 range test records the subject, lower bound and upper bound in that order. It records negation and symmetry independently and produces a nullable Boolean result. Its SQL uses the resolved pg_catalog comparisons even if the runtime search path contains another operator of the same name.
- A PostgreSQL null-safe int4 comparison compares two signed leaves and treats NULL as a comparable value. Its integer equality is bound to pg_catalog, and the result is always Boolean.
- A PostgreSQL native Boolean field owns a checked occurrence and column slot. The same reference role can appear in a SELECT, a checked predicate or a mutation RETURNING layout. A closed derived input exports the field by position.
- A PostgreSQL truth test owns a Boolean predicate and the precise IS TRUE, IS FALSE, IS UNKNOWN or negated operation. These tests always produce a nonnull Boolean.
- PostgreSQL projection casts retain their explicit operand and builtin int4, int8, Boolean or native text target. Int4 promotes to int8. Explicit int8 narrowing to int4 preserves in-range values and retains the native overflow error. Boolean integer conversions use int4. An untyped NULL can acquire an explicit native type. Compatible typed NULLs propagate, including inside set operations. The containing set operation promotes mixed int4 and int8 projections to int8.
- An explicitly cast PostgreSQL projection marker records its one-based position and native input type. The first use fixes the input type. A later use can add a native conversion while retaining its position and input type. Query arms share one parameter signature.
- DISTINCT compares complete projected rows. ORDER BY uses one-based output ordinals and fixes direction and NULL placement for each key. Apply LIMIT and OFFSET after ordering. PostgreSQL accepts a standalone OFFSET. A row bound may cut through a tie, where each choice remains valid within the original bag of typed rows.
- Top-level INSERT writes one or more checked VALUES rows into one resolved table. The ordered targets include writable signed integer columns in both dialects and native text columns in PostgreSQL. A supplied cell contains a checked literal or SQL NULL. Omitted columns use the same external defaults. The database applies constraints and triggers on execution.
- A query INSERT assigns each output of an independent SELECT to its explicit target column by position. It retains the source filter, duplicate policy and NULL values. PostgreSQL uses the destination kind for a bare NULL and admits a signed int4 literal or physical field in a text target slot under the stock native assignment conversion.
- PostgreSQL VALUES and query INSERT use a `Destination` with separate relation and ordered write slots. An optional ordered RETURNING layout reads the inserted row, including fields whose values come from database defaults.
- Top-level UPDATE preserves the ordered assignment list and optional filter over one resolved base table. Assignment operands are checked literals, SQL NULL or resolved field reads. MySQL reads the current row as assignments proceed. PostgreSQL reads the old row for assignments, supports ONLY and reads ordered int4 and native text RETURNING fields from the new row.
- Plain BEGIN, COMMIT, ROLLBACK, SAVEPOINT, RELEASE and ROLLBACK TO describe a connection-local transition. A named command stores the decoded checkpoint identifier. MySQL explicitly completes with NO CHAIN and NO RELEASE. The analyzed MySQL statement uses the `completion_type=0` profile for omitted options.
- DROP TABLE keeps the ordered absolute target identities and the missing-table policy. MySQL resolves session-local and persistent tables according to the explicit TEMPORARY modifier and the native name precedence. PostgreSQL retains CASCADE or RESTRICT for the persistent targets.
- CREATE TABLE fixes an absolute declaration identity, ordered native column kinds, nullability, literal defaults and IF NOT EXISTS. A MySQL `CreateTable` takes a `TableIdentity` with `BaseTable` or `TemporaryTable`. The temporary form uses the session namespace and survives rollback while pending row writes can roll back. PostgreSQL's ordinary table role uses heap and accepts builtin `pg_catalog.text` storage with the database default collation. Text defaults preserve decoded text, NULL and the native signed-to-text assignment. An unqualified `text` type requires a declaration context that resolves it to the builtin. [MySQL table declaration contract](../assurance/mysql-session-create-table-v1.json) [PostgreSQL text declaration contract](../assurance/postgres-create-text-v1.json)
- A compound query combines two checked SELECT arms. UNION, INTERSECT and EXCEPT preserve their tree grouping and row multiplicity policy. The leftmost arm supplies output names. MySQL 5.6 and 5.7 use a left-associated UNION tree. Arm ordering, bounds and WITH remain open.
- An explicit native integer cast on an output parameter fixes its position and target role. MySQL uses the lexical order of the question marks in a projection. PostgreSQL preserves numbered references, including repetitions and lexical reordering. The caller supplies the binding values. Other parameter positions and types remain open.
- A local projection reads resolved output ordinals from an independent derived SELECT. Each layer owns its labels and can reorder or repeat its immediate input slots. The MySQL local projection also covers an ordinary one-use CTE. MySQL 5.6 materializes the input and later profiles use `derived_merge=on`. MySQL integer values carry the effective width used when the server materializes a field.
- A PostgreSQL `WithProjection` owns the ordered definitions of an ordinary WITH statement. Each `WithRead` specifies the declaration and the ordered slots it reads. The value retains the materialization policy, keeps nested lexical scopes separate, and checks the common parameter types before construction succeeds.
- Filters and join conditions compose AND, OR, NOT, scalar IS NULL and IS NOT NULL. MySQL also has XOR. Each owning query, join or mutation checks predicate references in its visible layout. Only TRUE selects a row. PostgreSQL FULL joins require the checked opposite-side equality.
- A signed recursive series holds one initial literal, an increment, a strict continuation bound and the resolved reads of its working column. MySQL 8.0 and later and PostgreSQL emit the recursive binding from those operands. The output names follow the requested projection.
- A join leaf can hold a checked independent SELECT with signed integer fields. A consumer references the leaf by occurrence and reads the definition by ordinal. The leaf owns its SELECT and keeps its multiplicity, DISTINCT and filters. Derived leaves with ordering, bounds, dependent scopes or computed result fields remain open.
- A grouped projection partitions one resolved table by named signed slots or uses one global group. Each ordered output reads a grouping key or a native COUNT, SUM, MIN or MAX. COUNT distinguishes all admitted rows from nonnull argument values. DISTINCT applies within the aggregate, and SUM keeps the dialect’s native exact result type.
- Additional relation and predicate forms, grouping, expression ordering, other row bounds, further DML, further DDL and advanced transaction effects remain open in the native domains. Use the [scope and evidence guide](../assurance/README.md) for the implementation and engine coverage.

## Construction and evidence

| Requirement | Mechanism in the initial SQLite domain |
| --- | --- |
| P01 | The root identifies the language profile. Every operator has a closed enum case. Table identity and numbered parameters are explicit. Column references index local source slots. |
| P02 | Final classes close operand alternatives. Checked list construction copies arrays by value. The SELECT constructor checks scope, count and expanded expression limits before returning. Analysis uses the same constructor. |
| P03 | The root holds only a projection and its semantic source identity. A result name derived from SQL spelling is carried as the observed label and emitted as a quoted alias. |
| P04 | Each arithmetic node stores ordered operands. Expressions can be read or reconstructed by matching their concrete types. The source and references resolve locally in the root. |
| P05 | Every published property is readonly. The operand types and list element classes are closed. `Snapshot` blocks cloning, dynamic properties and PHP serialization and restoration. |
| P06 | The emitter visits every expression alternative, writes grouping explicitly, quotes identifiers, and emits a result name for every projection. Independent execution checks the observations on SQLite 3.47.2 within the recorded domain. |

The table applies to the checked projection roles. The SQLite [relational evidence record](../assurance/sqlite-relational-v4.json) adds checked join, predicate and ordering roles. The [result selection record](../assurance/sqlite-result-v1.json) covers duplicate equivalence, limit and offset composition, and allowed results when bounds cut through a tie. The [server projection record](../assurance/server-projection-v1.json), [server join record](../assurance/server-join-v2.json) and [server result record](../assurance/server-result-v1.json) specify the native conditions and observations. The full scope and status of the remaining obligations are recorded in the [contract ledger](../assurance/contract-v1.json) and the [evidence guide](../assurance/README.md).
